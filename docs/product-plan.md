## 1. Продукт, аудитория, позиционирование

### 1.1 Суть продукта

> **Пересмотр 30.10.2026 (ADR-0006).** Главный продукт — крипто-график для технического анализа: индикаторы,
> инструменты рисования, автоматическая разметка (уровни, зоны, структура, ликвидации) и пошаговый разбор по
> таймфреймам. Сигналы ниже — следующий этап; в меню и на главной их сейчас нет.

Веб-сервис и мобильное приложение, которое после закрытия каждой свечи H4 проверяет набор инструментов по формализованной торговой системе и публикует торговые сигналы: направление, зона входа, стоп-лосс, три тейк-профита, оценка уверенности и текстовое обоснование с графиком. Каждый сигнал затем отслеживается до завершения, результат фиксируется и попадает в публичную статистику, которую нельзя отредактировать задним числом.

Ключевой принцип: **правила открыты, статистика честная, перерисовки нет.** Пользователь видит, почему возник сигнал и что произошло со всеми предыдущими сигналами, включая убыточные.

### 1.3 Ценностное предложение

Одной фразой: «Проверяемые сигналы на H4 с честной статистикой каждой сделки, включая убыточные».

Опоры:
1. Формализованная система, правила описаны публично (без раскрытия точных параметров).
2. Сигнал всегда содержит вход, стоп, тейки, R:R и размер позиции под риск пользователя.
3. Статистика пишется автоматически, редактировать нельзя, экспорт доступен любому.
4. Сигнал публикуется только по закрытой свече — нет перерисовки.
5. Интерфейс профессионального терминала, а не маркетингового лендинга.

## 2. Логика генерации сигналов на H4

Всё ниже — детерминированные правила. Любой сигнал можно воспроизвести по историческим данным и получить тот же результат. Параметры (периоды, пороги) хранятся в конфиге стратегии с версией; каждый сигнал ссылается на версию стратегии, по которой он сгенерирован.

### 2.1 Входные данные

- Свечи OHLCV: H4, D1, W1 по каждому инструменту (минимум 400 свечей H4, 300 D1, 150 W1 истории).
- Объём в базовой валюте и в quote (USDT).
- Деривативные данные по perpetual-контрактам (Binance/Bybit REST и WebSocket): funding rate (текущий и история), open interest (OI) по 4-часовым интервалам, поток ликвидаций (`forceOrder`/`liquidation` стримы), long/short ratio топ-трейдеров. Хранятся в TimescaleDB рядом со свечами.
- Экономический календарь (FMP / Trading Economics API; у Investing.com официального API нет, парсинг не используем) — только макрособытия, влияющие на крипту: FOMC, CPI, NFP, решения по ставке.
- Крипто-события: даты разблокировок токенов (vesting, через Tokenomist/CryptoRank API), крупные делистинги, запланированные апгрейды сетей — помечаются в карточке, в v2 становятся фильтром.
- Корреляционная матрица по дневным доходностям за 90 дней (пересчёт раз в сутки); отдельно — бета альта к BTC.

### 2.2 Шаг 1. Контекст старшего таймфрейма (D1 и W1)

Для каждого инструмента на закрытии D1 вычисляем состояние тренда:

| Признак | Правило |
|---|---|
| Структура D1 | Последовательность swing high/low (фрактал: экстремум, у которого слева и справа по 2 свечи с меньшими high / большими low). Тренд вверх = последний HH и HL; вниз = LH и LL; иначе — флэт. |
| Фильтр EMA D1 | Цена закрытия относительно EMA50 D1 и наклон EMA50 за 10 свечей. |
| Направление W1 | Структура по тем же правилам на W1. |

Результат — `bias` для каждого инструмента: `long`, `short`, `neutral`.

- `long`: структура D1 вверх И закрытие > EMA50 D1 И W1 не против (вверх или флэт).
- `short`: зеркально.
- `neutral`: во всех остальных случаях — H4-сигналы по инструменту не генерируются (кроме стратегии «разворот», которая по умолчанию выключена, см. 2.9).

### 2.3 Шаг 2. Структура рынка на H4

На каждой закрытой свече H4:

1. **Swing-точки H4** — фрактал с 2 свечами по бокам (параметр `swing_len=2`, тестируем 2 и 3).
2. **BOS (Break of Structure)** — закрытие свечи H4 выше последнего swing high (в аптренде) или ниже последнего swing low (в даунтренде). Подтверждает продолжение.
3. **CHoCH (Change of Character)** — первое закрытие против текущего направления H4-структуры: в аптренде закрытие ниже последнего HL. Сигнализирует о смене локального направления; используется как условие **не входить** против свежего CHoCH и как триггер для стратегии разворота (v2).
4. **Фиксация импульса**: после BOS определяем импульсную ногу — от последнего swing low до нового high (для лонга).

### 2.4 Шаг 3. Зоны интереса

**Order block (OB):** последняя контртрендовая свеча перед импульсом, который произвёл BOS. Для лонга — последняя медвежья свеча перед импульсом вверх; зона = от её low до её open (консервативно) или до high (агрессивно, параметр). Зона валидна, пока цена не закрылась ниже её low.

**Зона спроса/предложения (S/D):** база консолидации (1–3 свечи с телом < 50 % диапазона) перед импульсом ≥ 1.5 ATR(14, H4). Если OB и S/D совпадают — одна зона с повышенным весом.

**Fair Value Gap (FVG):** трёхсвечный разрыв между high свечи 1 и low свечи 3 (для лонга). Используется как дополнительный вес, если зона входа пересекается с FVG.

**Ликвидность:**
- Равные максимумы/минимумы (разница < 0.1 ATR) — цель для снятия ликвидности.
- Снятие ликвидности (sweep): свеча пробила предыдущий swing low хвостом, но закрылась выше него. Sweep перед возвратом в OB — сильный плюс к скорингу.
- Дневные и недельные high/low предыдущего периода (PDH/PDL, PWH/PWL) — как уровни тейк-профитов и фильтр «не входить перед уровнем, если до него < 1 R».

### 2.5 Шаг 4. Фильтры

| Фильтр | Правило | Действие при непрохождении |
|---|---|---|
| ATR-режим | ATR(14, H4) / цена должен быть в диапазоне [p10; p90] за последние 200 свечей. Слишком низкая волатильность — флэт, слишком высокая — паника. | Сигнал не генерируется |
| Объём | Объём импульсной свечи BOS ≥ 1.2 × средний объём за 20 свечей H4 | Минус 15 баллов скоринга (не блокирует) |
| Сессии | Не блокирует (рынок 24/7). Отмечаем сессию (Азия/Европа/США) в карточке; свечи выходных (суббота–воскресенье) с объёмом < 0.6× среднего помечаются «низкая ликвидность», сигнал получает −5 баллов. | Информация / штраф |
| Новости | За 2 часа до и 1 час после событий высокой важности (FOMC, CPI, NFP, решения ЦБ) сигналы по всем инструментам помечаются «отложен» и публикуются после события, если условия сохраняются. | Отложить |

Экстремальный funding в сторону сигнала (для лонга ≥ +0.05 % за 8 ч, перцентиль > 95 за 90 дней) → перегрев, сигнал не генерируется. | Бонус / блок |

### 2.6 Шаг 5. Параметры сделки

Сетап для лонга (шорт зеркально):

1. Bias D1 = `long`.
2. На H4 произошёл BOS вверх, после него цена вернулась (ретест) в OB/S/D зону. Условие триггера: свеча H4 закрылась внутри зоны или выше неё, при этом хвост касался зоны. Сигнал формируется на закрытии этой свечи.
3. **Вход:** два варианта в карточке:
   - Рыночный: цена закрытия сигнальной свечи (используется для статистики по умолчанию).
   - Лимитный: середина зоны (50 % OB). Если цена не дошла за 6 свечей H4 (24 часа) — сигнал истекает.
4. **Стоп-лосс:** ниже low зоны минус буфер `max(0.25 × ATR(14,H4), 0.15 % цены)`. Если расстояние до стопа > 2.5 ATR — сигнал отклоняется (слишком широкий стоп).
5. **Тейк-профиты:**
   - TP1 = вход + 1.0 R (R = расстояние до стопа). Рекомендация: закрыть 40 %, перевести стоп в безубыток.
   - TP2 = ближайший структурный уровень (последний swing high / PDH / равные максимумы), но не ближе 1.8 R и не дальше 3 R. Закрыть 40 %.
   - TP3 = следующий структурный уровень или 4 R (что ближе). Закрыть 20 %.
6. **Минимальный R:R:** TP2 / риск ≥ 1.8. Иначе сигнал не публикуется. Ожидаемый средний R при винрейте 45 % должен быть положительным (см. 2.11).
7. **Срок жизни:** лимитный вход — 24 часа ожидания; активная сделка — максимум 15 свечей H4 (60 часов) до TP1, иначе закрытие по рынку с фиксацией результата (правило «time stop»). После TP1 — без ограничения времени, до TP3 или стопа в безубытке.

### 2.7 Скоринг уверенности (0–100)

| Компонент | Баллы | Условие |
|---|---|---|
| Согласие W1 с D1 | 0 / 15 | W1 в ту же сторону — 15, флэт — 7, против — сигнал не генерируется |
| Сила BOS | 0–15 | Закрытие за уровнем на ≥ 0.3 ATR — 15; 0.1–0.3 — 8; меньше — 0 |
| Качество зоны | 0–20 | OB + S/D + FVG совпали — 20; два из трёх — 12; один — 6 |
| Снятие ликвидности перед входом | 0 / 15 | Sweep в пределах 10 свечей до ретеста |
| Объём на импульсе | 0–10 | ≥ 1.5× среднего — 10; 1.2–1.5× — 5 |
| R:R до TP2 | 0–15 | ≥ 3 — 15; 2.5–3 — 10; 1.8–2.5 — 5 |
| Отсутствие близких препятствий | 0–10 | Нет PDH/PWH/равных максимумов/плотного кластера ликвидаций между входом и TP1 — 10 |
| Деривативы | −10…+25 | Funding против сигнала +10; подтверждение OI +5 / short-squeeze −5; каскад ликвидаций в зону +10; толпа в сторону сигнала −5 (см. 2.5) |
| Штрафы | до −35 | Коррелирующий активный сигнал −10; новость в ближайшие 12 ч −10; ATR в верхнем дециле −10; свеча выходного дня с низким объёмом −5 |

Сумма ограничивается диапазоном 0–100. Градации в интерфейсе: **A** (≥ 75), **B** (55–74), **C** (40–54). Сигналы ниже 40 не публикуются, но сохраняются в базе для анализа. Тариф Free видит только A-сигналы с задержкой, см. раздел 4.

Веса скоринга — параметры стратегии; меняются только через новую версию стратегии после бэктеста. Правило: скоринг должен иметь монотонную связь с результатом на бэктесте (средний R у A > B > C), иначе веса пересматриваются.

### 2.8 Отсутствие перерисовки (no repaint)

- Все вычисления выполняются только по **закрытым** свечам. Текущая незакрытая свеча не участвует.
- Фракталы с 2 свечами справа означают, что swing-точка подтверждается с задержкой в 2 свечи. Это учитывается честно: сигнал может использовать только swing-точки, подтверждённые на момент сигнальной свечи.
- Сигнал публикуется в течение 60 секунд после закрытия H4 с фиксацией `created_at` и хэшем входных данных (последние 400 свечей). После публикации поля входа/стопа/тейков **неизменяемы**.
- Любое изменение (например, перевод стопа в безубыток после TP1) записывается как событие с таймстемпом, а не как перезапись.
- Воспроизводимость: эндпоинт `replay(strategy_version, symbol, candle_close_time)` должен вернуть идентичный сигнал. Это автоматический тест в CI.

### 2.9 Стратегии как сущности

Движок поддерживает несколько стратегий, каждая с версией и статусом (`backtest`, `forward`, `live`, `archived`):

| Стратегия | Описание | Статус на MVP |
|---|---|---|
| `trend-ob-retest` | Описана выше: продолжение тренда через ретест OB после BOS | live |
| `liquidity-sweep-reversal` | Разворот после снятия дневной ликвидности и CHoCH на H4, вход по ретесту | forward (публикуется в отдельной вкладке «Эксперимент», не входит в основную статистику) |
| `range-fade` | Торговля от границ подтверждённого диапазона D1 | backtest |

Новая стратегия выходит в `live` только после: бэктест ≥ 3 лет, ≥ 200 сделок, профит-фактор ≥ 1.4, затем форвард ≥ 3 месяца с результатом в пределах доверительного интервала бэктеста.

### 2.10 Жизненный цикл сигнала

```
pending ──(цена дошла до лимитного входа / рыночный вход сразу)──► active
pending ──(24 ч без входа / отмена по CHoCH)──► expired
active ──(цена коснулась TP1)──► tp1_hit ──► стоп на безубыток
tp1_hit ──(TP2)──► tp2_hit ──(TP3)──► closed_tp3
tp1_hit / tp2_hit ──(цена вернулась к входу)──► closed_be
active ──(цена коснулась SL)──► closed_sl
active ──(15 свечей H4 без TP1)──► closed_time
любой active-статус ──(ручная отмена админом с причиной)──► cancelled (учитывается в статистике как 0 R, видно всем)
```

Отслеживание ведётся по тиковым/минутным данным (WebSocket aggTrade или kline 1m), а не по H4, чтобы корректно фиксировать касания. Правило разрешения конфликта: если в одной минутной свече были и TP, и SL — считается **SL** (консервативно). Это правило указано публично.

Результат сделки в R считается по рекомендованной схеме частичного закрытия (40/40/20) и фиксируется в `realized_r`. Дополнительно сохраняем `r_if_tp1_only`, `r_if_full_tp2` для прозрачности.

### 2.11 Бэктест, форвард-тест, публичная статистика

**Бэктест:**
- Данные: исторические свечи H4/D1/W1 с бирж за ≥ 4 года (2022–2026) по всему списку инструментов плюс делистнутые пары (чтобы избежать survivorship bias).
- Исполнение: вход по закрытию сигнальной свечи (или лимит), проверка касаний по 1m-данным; комиссия 0.05 % за сторону (тейкер), проскальзывание 0.03 %; funding не учитываем в MVP (указано).
- Выход бэктеста: список сделок, equity-кривая в R, метрики ниже, разбивка по инструментам, по градации скоринга, по году и по месяцу.
- Walk-forward: оптимизация параметров на 2022–2024, проверка на 2025–2026. Параметры фиксируются после проверки; переобучение запрещено до следующей версии стратегии.

**Форвард-тест:** стратегия работает на живых данных в режиме `forward` минимум 3 месяца до публикации пользователям; сигналы форварда сохраняются с тем же пайплайном.

**Метрики (публичные, на странице /stats и в каждой карточке стратегии):**

| Метрика | Определение |
|---|---|
| Количество сигналов | Всего / закрытых / активных / истёкших |
| Винрейт | Доля сделок с `realized_r > 0` среди закрытых. Нейтральными (показываются отдельно) считаются только сделки с `realized_r = 0` — например, `closed_time` около входа. `closed_be` после TP1 даёт +0.4 R по схеме 40/40/20 и считается выигрышем; дополнительно публикуется «винрейт до TP1» (доля сделок, дошедших до TP1 раньше стопа) |
| Средний R | Сумма `realized_r` / число закрытых сделок (включая убыточные и BE) |
| Профит-фактор | Сумма положительных R / |сумма отрицательных R| |
| Expectancy | Винрейт × средний выигрыш − (1 − винрейт) × средний проигрыш, в R |
| Максимальная просадка | В R и в % при фиксированном риске 1 % на сделку, по закрытым сделкам в хронологическом порядке |
| Серии | Максимальная серия убытков подряд |
| Доля TP1/TP2/TP3 | Процент сигналов, достигших каждого уровня |
| Среднее время в сделке | Часы от входа до закрытия |

**Правила честности (закрепляются в коде и в публичной оферте):**
1. Сигнал нельзя удалить или изменить после публикации. Удаление возможно только через статус `cancelled` с публичной причиной.
2. Статистика пересчитывается автоматически из таблицы сигналов; ручной ввод отсутствует.
3. Истёкшие (не вошедшие) сигналы показываются отдельно и не входят в винрейт, но их количество публично.
4. Публикуется полная история, включая убыточные, с экспортом CSV для всех зарегистрированных пользователей.
5. Бэктест помечается как бэктест, форвард как форвард, live как live. Смешивать запрещено.
6. Отдельно показываем «статистику по рыночному входу» и «по лимитному входу», так как у них разные результаты.

## 2A. Терминал-график и анализ паттернов

Отдельный модуль продукта по требованию заказчика: полноценный собственный график со всеми индикаторами, адаптированный под телефон, со встроенным анализом свечных паттернов и графических фигур. Нумерация «2A» выбрана, чтобы не сдвигать ссылки на разделы 3–12. Экран описан в 3.17, тарифные ограничения — в разделе 4, задачи — в 10.3.

### 2A.1 Назначение и границы

- График — рабочее место трейдера внутри сервиса: смотреть любой инструмент на любом таймфрейме, накладывать индикаторы и наши слои (структура, зоны, сигналы), рисовать, ставить алерты, читать найденные паттерны и их историческую отработку.
- График **не** генерирует сигналы. Сигналы — только движок раздела 2. Паттерны и фигуры с графика попадают в скоринг сигналов только через новую версию стратегии после бэктеста (2A.10.5).
- Один и тот же компонент графика используется в карточке сигнала (3.5, урезанный режим), на экране «График» (3.17, полный режим) и в мобильном приложении.

### 2A.2 Выбор движка

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **TradingView Lightweight Charts v5** (Apache 2.0) + собственные слои | 45 КБ, Canvas, высокая производительность на мобильных, активная поддержка; v5 даёт несколько панелей (panes), API примитивов (`ISeriesPrimitive`/`IPanePrimitive`) для своих отрисовок, кастомные серии; полный контроль над UI — рисуем свои тулбары, меню, жесты | Нет встроенных индикаторов и инструментов рисования — всё пишем сами (расчёт индикаторов, drawings, магнит к OHLC, редактирование точек); нет Heikin Ashi из коробки (считаем сами, тривиально); требуется атрибуция | **Рекомендуем.** Надёжный рендер, а UI, индикаторы, рисование и жесты — свои, что совпадает с требованием заказчика к дизайну и мобильной адаптации |
| **KLineChart** (Apache 2.0) | Встроены ~50 индикаторов, инструменты рисования (overlays), панели, тач-жесты; меньше писать | Меньше сообщество, API менее стабилен между версиями, стиль и поведение рисовалок придётся переопределять, чтобы соответствовать разделу 5; расчёты индикаторов внутри библиотеки — сложнее гарантировать идентичность с серверным расчётом (нужна для алертов и паттернов) | Запасной вариант: если за 2 недели прототипа на LWC станет ясно, что объём своих слоёв недооценён. Решение фиксируется ADR |
| **TradingView Advanced Charts** (Charting Library) | Полный терминал: индикаторы, рисование, шаблоны, мобильные жесты | Закрытый код, выдаётся по заявке и одобрению TradingView (сервисам сигналов могут отказать), обязательная атрибуция и ограничения на изменение UI, свой стиль (выглядит как TradingView, а не как наш продукт), сложно встроить наши слои и паттерны глубоко, нельзя форкать | Отклоняем: теряем контроль над дизайном и зависим от одобрения |
| **Собственный рендер на Canvas/WebGL с нуля** | Полный контроль, WebGL-масштабируемость на 100k+ свечах | 3–5 месяцев работы только на базовый рендер (шкалы, зум, кинетика, панели, ретина, сглаживание), высокий риск багов, отвлекает от продукта | В MVP нет. Возможен в v3 как замена рендера под нашим же слоем API, если упрёмся в ограничения LWC |

Решение: **Lightweight Charts v5 как рендер + пакет `packages/charts`** (TypeScript, без зависимости от React) со своими слоями: расчёт индикаторов, панели, инструменты рисования, жесты, темы. React-обёртка отдельно. Расчёт индикаторов — одна и та же TypeScript-библиотека на клиенте и в Node-воркере алертов; параллельная Python-реализация в `engine/` сверяется golden-тестами (одинаковый вход → одинаковый выход с точностью 1e-8), чтобы паттерны, алерты и график показывали одно и то же.

### 2A.3 Таймфреймы, типы графиков, данные

- Таймфреймы: 1m, 5m, 15m, 1h, **4h (по умолчанию)**, 1d, 1w. Переключатель показывает H4 первым и крупнее. Таймфреймы 1m–15m на тарифе Free недоступны (см. раздел 4) — они не нужны для нашей системы и дороги по трафику.
- Данные: сервер хранит 1m, 4h, 1d, 1w (раздел 6.4); 5m/15m/1h агрегируются на сервере из 1m через continuous aggregates TimescaleDB. Клиент получает историю порциями по 500 свечей через REST (`/candles?symbol&tf&before`) и обновление текущей свечи через WebSocket. Текущая незакрытая свеча помечена визуально (контур вместо заливки) — пользователь всегда видит, что она ещё не закрыта.
- Типы графиков: японские свечи, бары (OHLC), линия (по close), Heikin Ashi (считается на клиенте из обычных свечей; все паттерны и алерты работают только по обычным свечам, в режиме HA это написано в подсказке). Area, Renko, Kagi — не делаем.
- Шкалы: линейная и логарифмическая, автомасштаб, фиксация шкалы, процентная шкала при сравнении инструментов (v2: наложение второго инструмента, например альт против BTC).
- Отметки времени — UTC и локальное по настройке, вертикальные разделители суток и недель, отметки закрытия H4 чуть заметнее остальных.
- На графике всегда доступны: последняя цена с меткой, countdown до закрытия текущей свечи, funding и время следующего funding (perpetual), 24h объём — в компактной строке над графиком.

### 2A.7 Мобильная адаптация

Телефон — основной сценарий для сегмента A, поэтому мобильная версия графика проектируется первой, а не ужимается из десктопной.

**Компоновка (портрет):**
- Верх (44 px): инструмент (тап — поиск с клавиатурой), таймфрейм (тап — ряд чипов, H4 крупнее), кнопка «ещё».
- График занимает всю ширину; ценовая шкала справа 56 px, временная внизу 20 px.
- Панели индикаторов под графиком: каждая 72–96 px высотой, сворачиваются до заголовка 24 px свайпом вниз; не больше 3 раскрытых одновременно (остальные свёрнуты), горизонтальная прокрутка не используется.
- Нижняя кнопочная строка (48 px, зоны касания 44×44): индикаторы, рисование, алерт, слои, паттерны. Любая открывает **bottom sheet** (нижний лист): высота 50 % экрана, тянется до 90 %, закрывается свайпом; внутри — списки и формы с полями 44 px высотой, без вложенных модалок.
- Строка состояния над графиком: последняя цена, изменение, countdown до закрытия, funding — одна строка моноширинным.

**Жесты:**
| Жест | Действие |
|---|---|
| Горизонтальный pan одним пальцем | Прокрутка по времени; кинетика с затуханием; у правого края — «догнать текущую свечу» |
| Pinch | Зум по времени вокруг точки между пальцами; вертикальный pinch на ценовой шкале — зум по цене |
| Pan по ценовой шкале | Сдвиг шкалы, автомасштаб выключается; двойной тап по шкале — вернуть автомасштаб |
| Long-press (300 мс) | Перекрестие с «липким» режимом: панель OHLCV + значения индикаторов + найденные паттерны на этой свече появляется над графиком (не тултипом у пальца); водя пальцем, видим значения; отпустил — перекрестие остаётся до тапа в пустое место |
| Двойной тап | Сброс масштаба к последним 120 свечам и автомасштабу |
| Тап по объекту (зона, сигнал, рисунок, паттерн) | Выделение + контекстная карточка внизу (bottom sheet 30 %) с действиями |
| Тап по пустому месту в режиме рисования | Постановка точки; точки редактируются перетаскиванием за увеличенные хэндлы (28 px); лупа над пальцем при точном позиционировании |
| Свайп по панели индикатора вниз/вверх | Свернуть/развернуть панель |
| Поворот телефона | Ландшафтный режим: скрываются верх и нижняя строка (появляются по тапу), график на весь экран, шкалы тоньше, панели индикаторов справа в виде вертикальной колонки или под графиком по настройке; блокировка ориентации доступна |

Конфликт жестов: горизонтальный pan приоритетнее вертикальной прокрутки страницы — график перехватывает touch-события в своей области (`touch-action: none`), а страница скроллится только за пределами графика; на экране «График» страница вообще не скроллится.

**Производительность и ограничения:**
- Целевая кадровая частота 60 fps при pan/zoom на устройствах уровня iPhone 11 / Android среднего класса 2021 года (тестовые устройства закрепляются в ТЗ). Бюджет кадра — 16 мс: рендер LWC + наши примитивы ≤ 10 мс.
- В памяти не более 5 000 свечей текущего таймфрейма; при прокрутке влево — ленивая подгрузка по 500 свечей с индикатором загрузки на левом краю; при уходе вправо старые выгружаются. Индикаторы пересчитываются инкрементально (только новые свечи), а не по всему массиву.
- Рисунки и слои отрисовываются только в видимом диапазоне (culling); при pan объекты за экраном не считаются.
- Тяжёлые расчёты (Volume Profile, CVD, поиск фигур) — на сервере или в Web Worker, не в главном потоке.
- Снижение детализации: при pinch в активной фазе скрываются подписи паттернов и значения на шкале рисунков; возвращаются через 150 мс после окончания жеста.
- Экономия батареи и трафика: WebSocket только для видимого инструмента, частота обновления свечи не выше 2 раз/с, фон — отключение сокета через 30 с.
- Метрики производительности (время первого кадра, доля кадров > 16 мс, время подгрузки) отправляются в Sentry Performance; порог алерта: доля медленных кадров > 5 % на поддерживаемых устройствах.

**PWA и React Native:**
- PWA: тот же `packages/charts` на Canvas; `touch-action: none`, обработка `pointer events`, предотвращение pull-to-refresh в области графика, `safe-area-inset` для iPhone, установка на домашний экран рекомендуется для полноэкранного режима.
- React Native (этап 4): LWC работает в WebView (`react-native-webview`) с тем же пакетом `packages/charts`; обмен через postMessage, данные свечей передаются бинарно (ArrayBuffer base64) порциями. Нативные слои: верхняя панель, bottom sheet (`@gorhom/bottom-sheet`), клавиатура поиска — нативные, график — WebView. Если замеры покажут < 50 fps на устройствах уровня целевых, переходим на нативный рендер через `react-native-skia` для свечей и серий (отдельная задача этапа 4 с прототипом в первую неделю).
- Офлайн: последние 500 свечей видимых инструментов и все рисунки кэшируются (IndexedDB / AsyncStorage); график открывается без сети с пометкой «данные на HH:MM».

### 2A.10 Анализ на графике: паттерны, фигуры, объяснения

Честное описание того, что здесь «ИИ»: детерминированные правила для свечных паттернов, алгоритмический поиск плюс ML-ранжирование для графических фигур, LLM только для текста. Ничто из этого не является сигналом.

#### 2A.10.1 Свечные паттерны — детерминированные правила (MVP)

Сервис `pattern-detector` (Python, модуль `engine/patterns`, та же кодовая база, что и бэктест) запускается на закрытии каждой свечи каждого таймфрейма от 15m до 1w (1m/5m — только по запросу на клиенте с той же TS-библиотекой). Все паттерны считаются только по **закрытым** свечам. Нормировка размеров — через ATR(14) того же таймфрейма и средний диапазон тела за 20 свечей.

Общие обозначения: `body = |close − open|`, `range = high − low`, `upper = high − max(open, close)`, `lower = min(open, close) − low`, `avg_body` — среднее тело за 20 свечей.

| Паттерн | Правило (бычий вариант; медвежий зеркально) | Контекст (обязателен для статуса «значимый») |
|---|---|---|
| Поглощение (engulfing) | Свеча 2 бычья, свеча 1 медвежья; `open2 ≤ close1` и `close2 ≥ open1`; `body2 ≥ 1.2 × avg_body` | После ≥ 3 свечей снижения или у нижней границы зоны/уровня; объём свечи 2 ≥ 1.2× среднего |
| Пин-бар / молот | `lower ≥ 2 × body`, `upper ≤ 0.3 × range`, `body ≥ 0.1 × range`; закрытие в верхней трети | Хвост проткнул уровень/зону/равные минимумы (sweep) и закрылся обратно — максимальный вес |
| Повешенный / падающая звезда | Зеркально молоту сверху | После ≥ 3 свечей роста |
| Доджи | `body ≤ 0.1 × range`, `range ≥ 0.8 × ATR` | Отмечается как «нерешительность», сам по себе не направленный; «стрекоза»/«надгробие» — отдельно |
| Утренняя / вечерняя звезда | Свеча 1 — большая медвежья (`body ≥ 1.0 × avg_body`); свеча 2 — маленькая (`body ≤ 0.3 × avg_body`), гэп тела не обязателен (крипта); свеча 3 — бычья, закрытие выше середины свечи 1 | После снижения; объём свечи 3 ≥ среднего |
| Три белых солдата / три чёрные вороны | Три последовательные свечи в одном направлении, каждая закрывается выше предыдущей, тела ≥ 0.8 × avg_body, верхние тени ≤ 0.3 × body | Начинается от зоны/уровня; при `range` суммарно > 3 ATR помечается «перегрев» |
| Харами | Свеча 2 целиком внутри тела свечи 1, `body1 ≥ 1.2 × avg_body` | Только как «пауза», направленности нет без подтверждения следующей свечой |
| Внутренний бар (inside bar) | `high2 ≤ high1` и `low2 ≥ low1` | Пробой внутреннего бара отмечается отдельным событием |
| Пробойная свеча (marubozu) | `upper + lower ≤ 0.1 × range`, `body ≥ 1.5 × avg_body` | Пробой уровня/зоны — помечается как возможный BOS, сверяется со структурой |
| Пинцет (tweezer top/bottom) | Два соседних экстремума с разницей ≤ 0.1 × ATR, свечи разного направления | У уровня |

Контекстные признаки добавляются к каждому найденному паттерну как факты: направление тренда на этом и старшем таймфрейме, расстояние до ближайшей зоны/уровня в ATR, относительный объём, наличие sweep, положение относительно EMA50. Паттерн без контекста показывается бледно («найден»), с контекстом — «значимый». Это два разных статуса, а не оценка «силы сигнала».

#### 2A.10.2 Графические фигуры — алгоритм + ML-ранжирование (v2)

**Шаг 1. Алгоритмический поиск кандидатов** (`engine/figures`, детерминированный):
- Основа — swing-точки по фракталу (как в 2.3) на трёх масштабах (`swing_len` 2, 3, 5), чтобы ловить фигуры разного размера. Фигура описывается последовательностью swing-точек и допусками в ATR.
- Шаблоны и допуски:
  - Двойная вершина/дно: два экстремума с разницей ≤ 0.3 ATR, между ними откат ≥ 1.5 ATR, линия шеи — промежуточный экстремум; подтверждение — закрытие за линией шеи.
  - Голова и плечи (и перевёрнутые): три пика, средний выше крайних на ≥ 0.5 ATR, плечи с разницей ≤ 0.5 ATR, линия шеи по двум впадинам с наклоном ≤ 15°; подтверждение — закрытие за шеей; цель — высота головы от точки пробоя.
  - Треугольники (симметричный, восходящий, нисходящий): ≥ 2 касания каждой из двух сходящихся линий (регрессия по swing-точкам, R² ≥ 0.9), сжатие диапазона ≥ 40 %, длина 15–80 свечей; подтверждение — закрытие за линией в пределах первых 75 % длины до вершины.
  - Флаг / вымпел: импульс ≥ 2.5 ATR за ≤ 8 свечей (флагшток), затем консолидация 5–20 свечей в параллельном канале с наклоном против импульса (флаг) или сходящемся (вымпел), с диапазоном ≤ 50 % флагштока; подтверждение — закрытие за каналом в направлении импульса.
  - Клинья (восходящий/нисходящий): две сходящиеся линии одного наклона, ≥ 3 касаний суммарно, длина 20–100 свечей.
  - Канал (восходящий/нисходящий/горизонтальный = диапазон): две параллельные линии (разница наклонов ≤ 5°), ≥ 2 касания каждой.
  - Чашка с ручкой: U-образное дно (аппроксимация параболой, R² ≥ 0.8), глубина 1.5–6 ATR, длина 30–200 свечей, ручка — откат ≤ 1/3 глубины за 5–25 свечей; подтверждение — закрытие выше края чашки.
- Для каждого кандидата вычисляется **геометрический скор качества** 0–1: симметрия, число касаний, R² линий, соблюдение пропорций, объёмный профиль (падение объёма внутри консолидации, рост на пробое). Кандидаты с качеством < 0.4 отбрасываются.

**Шаг 2. ML-ранжирование** (`ml/figures-ranker`):
- Задача: по кандидату ответить, «настоящая ли это фигура, которую опытный аналитик пометил бы на графике», и ранжировать. Модель не предсказывает цену.
- Признаки: геометрические метрики кандидата, нормализованное окно цен (окно фигуры + 20 свечей до, приведённое к [0;1] по цене и к фиксированной длине 128 по времени), нормализованный объём, ATR-режим, таймфрейм, положение относительно структуры D1.
- Модели: базовая — градиентный бустинг (LightGBM) на табличных признаках; вторая — 1D-CNN на нормализованных окнах (цена+объём, 2 канала × 128); итог — усреднение вероятностей. Начинаем с бустинга (проще, объяснимее через SHAP), CNN добавляем, если даёт прирост ≥ 3 п.п. по PR-AUC на отложенной выборке.
- **Разметка данных:** разметчики — 2–3 трейдера с опытом (включая заказчика), независимо; инструмент разметки — внутренняя страница в админке: показывается кандидат на графике без подсказок и три кнопки «фигура», «не фигура», «не уверен», плюс тип. Метка принимается при согласии ≥ 2 из 3; согласованность (Cohen's kappa) публикуется в отчёте, цель ≥ 0.6. Объём: ≥ 600 размеченных кандидатов на тип фигуры (по ~10 типам — 6–8 тысяч, ≈ 60–80 часов разметки суммарно), стратификация по инструментам и годам, отложенная выборка — 2026 год целиком (временной сплит, не случайный). Хранится в `ml_labels`.
- **Обучение и метрики:** кросс-валидация по времени; целевые метрики на отложенной выборке — precision ≥ 0.75 при recall ≥ 0.6 по каждому типу; PR-AUC публикуется в карточке модели; отдельная проверка, что модель не деградирует по инструментам с низкой волатильностью. Порог вероятности выбирается по precision (нам важнее не показывать ложное).
- **Версионирование:** `ml_models` — версия, дата, датасет (хэш), гиперпараметры, метрики, статус (`candidate`/`shadow`/`live`/`archived`). Новая модель минимум 4 недели работает в `shadow` (её результаты записываются, но не показываются), сравнивается с текущей, выходит в live после ревью человека (10.4). Каждая отметка фигуры хранит `ml_model_id` и вероятность. Переобучение — не чаще раза в квартал, с добавлением новых меток.
- Что показываем пользователю: только фигуры с вероятностью ≥ порога; рядом — качество геометрии и **историческая отработка** этого типа (2A.10.4). Вероятность модели пользователю не показываем как «уверенность ИИ», чтобы не выглядело предсказанием; в подробностях — «ранжирование модели v1.2: прошло».

#### 2A.10.3 LLM (Claude) — только текст по фактам

- Назначение: (1) объяснение найденного на графике понятным языком; (2) ответ на вопрос пользователя о текущем графике («что здесь происходит?», «почему зона считается активной?», «что значит этот паттерн?»).
- Жёсткий контракт **«факты на входе → текст на выходе»**: шлюз `llm-gateway` собирает структурированный JSON фактов из движка (структура, зоны, индикаторы, найденные паттерны и их статистика, активные сигналы, деривативные метрики, события календаря) и передаёт в модель с системным промптом, который запрещает называть любые цены, уровни и цифры, отсутствующие во входных фактах, запрещает рекомендации («покупайте», «входите»), прогнозы и оценку вероятности, требует указывать источник факта. Выход проходит **постпроверку**: все числа в ответе сопоставляются регулярными выражениями с числами во входных фактах (с допуском форматирования); при расхождении ответ отбрасывается и показывается шаблонный текст из фактов. Ответ помечается «Текст составлен по данным графика на HH:MM UTC».
- Модель: Claude Haiku-класса для объяснений (дёшево, быстро), Sonnet-класса — для вопросов на тарифе Premium. Контекст ≤ 4 000 токенов входа, ≤ 400 выхода.
- Ограничения частоты: Free — нет LLM (только шаблонные тексты); Pro — 20 запросов/сутки; Premium — 100/сутки. Объяснения паттернов кэшируются по ключу `(instrument, tf, candle_close_time, facts_hash, locale)` в Redis на 24 часа — один паттерн объясняется один раз для всех пользователей. Ответы на вопросы кэшируются по нормализованному вопросу + facts_hash на 1 час.
- Стоимость: оценка при 1 000 активных Pro-пользователей с 5 запросами/день (половина из кэша): ≈ 2 500 некэшированных запросов × ~4 400 токенов ≈ 11 M токенов/день — при ценах Haiku-класса ≈ 10–15 USD/день, ≈ 0.3–0.45 USD/пользователя/мес; Premium на Sonnet-классе — ≈ 1.5–3 USD/пользователя/мес при полном лимите. Бюджет контролируется: лимит расхода в сутки на шлюзе, при превышении — переход на шаблонные тексты с уведомлением админу. Точные цены — по прайсу Anthropic на момент внедрения.
- Безопасность: входные факты — только серверные; текст пользователя передаётся как данные с ограничением 500 символов, инструкции в нём игнорируются (разделение ролей в промпте, проверка выхода); логи запросов хранятся 30 дней без привязки к персональным данным сверх user_id.

#### 2A.10.4 Без перерисовки, статус «формируется», публичная статистика отработки

- Паттерн или фигура получают статус **подтверждён** только на закрытой свече (для фигур — на закрытии свечи пробоя). До этого фигура может показываться в статусе **формируется** (пунктирный контур, без цели и без статистики), если геометрический скор ≥ 0.6 и не хватает только подтверждения. Переход «формируется → подтверждён / отменён» записывается событием в `pattern_events`. Подтверждённые отметки не удаляются и не сдвигаются; если позже структура изменилась — добавляется событие «не отработал».
- **Отработка** считается автоматически для каждого подтверждённого паттерна: через N свечей (N = 3, 5, 10 для свечных; до цели или 20 свечей для фигур) фиксируется, пошла ли цена в ожидаемую сторону на ≥ 1 ATR (свечные) или достигла ли расчётной цели / пробила ли инвалидацию (фигуры), а также максимальное движение в сторону и против в ATR. Поля — в `pattern_outcomes`.
- **Публичная статистика** на странице `/stats/patterns` и в карточке каждого паттерна: по типу × таймфрейм × инструмент (и агрегированно): число случаев, доля отработки, средний ход в ATR, с разбивкой «с контекстом / без контекста» и по году. Статистика считается из `pattern_outcomes` без ручного ввода; показывается с `n` и доверительным интервалом (Уилсон, 95 %). Если n < 30 — пишем «мало данных», а не процент. Так пользователь видит, что, например, доджи на H4 без контекста отрабатывает около 50 % и ничего не значит.
- Бэкфилл: при вводе нового типа паттерна или новой версии правил детектор прогоняется по истории (4 года) и статистика появляется сразу, с пометкой «историческая (бэкфилл)», live-статистика накапливается отдельно. Версия правил (`pattern_rules_version`) хранится в каждой отметке; смена правил — новая версия, старые отметки не пересчитываются задним числом.

#### 2A.10.5 Связь с сигналами

- Паттерны и фигуры **не являются сигналами** и не публикуются в ленте сигналов. Это слои графика и алерты.
- Они могут стать компонентами скоринга стратегии (например, «пин-бар с sweep на ретесте OB: +5») только через новую версию стратегии в статусе `backtest`, после доказательства на бэктесте, что компонент повышает средний R или монотонность градаций (2.7), затем через форвард (2.9). До этого в карточке сигнала они показываются как «дополнительные наблюдения» без баллов.
- Обратная связь: статистика отработки паттернов на H4 из 2A.10.4 — вход для решения, какие паттерны вообще тестировать в стратегии.

#### 2A.10.6 Тексты в интерфейсе

Разрешено: «найдено», «подтверждено на закрытии свечи», «формируется», «историческая отработка X % (n=…)», «текст составлен по данным графика». Запрещено: «ИИ предсказывает», «ИИ рекомендует», «сигнал на покупку/продажу» применительно к паттернам, «вероятность роста», «точность 90 %». Это правило добавляется в чеклист ревью текстов (раздел 8, п. 2) и в CLAUDE.md.

## 3. Функционал по экранам

Обозначения: **MVP** — в первом публичном релизе; **v2** — через 2–4 месяца после MVP; **v3** — 6+ месяцев.

### 3.1 Лендинг (публичный) — MVP

Что на экране:
- Первый экран: заголовок с сутью («Сигналы на H4 с публичной статистикой каждой сделки»), живой блок с последними 5 сигналами (реальные данные, обезличенные детали для незарегистрированных: инструмент, направление, градация, результат), ключевые метрики live-статистики за 90 дней (винрейт, средний R, количество сделок, просадка) с датой обновления.
- Блок «Как это работает»: 4 шага с реальным скриншотом карточки сигнала.
- Блок «Правила системы» — краткое описание логики из раздела 2 человеческим языком.
- Блок «Статистика» — встроенная equity-кривая в R, таблица по месяцам, ссылка на полную историю.
- Тарифы.
- FAQ (8–10 вопросов, включая «Почему вы не обещаете доходность»).
- Футер: дисклеймер, документы, контакты, ссылка на Telegram-бота.

Действия: перейти к регистрации, посмотреть открытую статистику, посмотреть пример карточки сигнала.

### 3.2 Регистрация / вход — MVP

- Email + пароль (минимум 10 символов, проверка по словарю утечек через HIBP k-anonymity), подтверждение email.
- Google OAuth.
- Telegram Login Widget (привязывает Telegram ID — сразу готово для бота).
- Восстановление пароля, magic link по email.
- 2FA (TOTP) — v2.
- Объединение аккаунтов, если один email вошёл разными способами.
- Чекбокс согласия с условиями и дисклеймером (обязателен), чекбокс рассылки (необязателен).
- Выбор страны (для юрисдикционных ограничений, см. раздел 8).

### 3.3 Онбординг — MVP

Три шага, каждый можно пропустить:
1. Опыт (новичок / опытный / системный) — влияет на подсказки и дефолтные настройки уведомлений.
2. Параметры риска: размер депозита (не сохраняем точную сумму без согласия, можно оставить пустым), риск на сделку (по умолчанию 1 %), биржа (Binance / Bybit — влияет на тикеры и ссылки).
3. Каналы уведомлений: подключить Telegram-бота (deep link с токеном), push (PWA), email-дайджест.

Завершение — переход в ленту с подсвеченным первым активным сигналом и подсказкой «Что значит R».

### 3.4 Лента сигналов (главный экран) — MVP

Структура — плотная таблица, не карточки:

| Колонка | Содержимое |
|---|---|
| Время | Время свечи закрытия (UTC и локальное), сколько прошло |
| Инструмент | Тикер, биржа, мини-спарклайн 24 свечи H4 |
| Направление | LONG/SHORT текстом с цветовой меткой |
| Градация | A/B/C и числовой скор |
| Вход / SL / TP1 / TP2 / TP3 | Цены с табличными цифрами |
| R:R | До TP2 |
| Статус | pending / active / tp1 / ... с цветовой меткой и временем последнего события |
| Текущий P&L в R | Живой, по WebSocket |
| Действия | Открыть, добавить в журнал, в вотчлист |

Фильтры (сохраняются в URL): статус, инструмент, направление, градация, стратегия, период. Сортировка по любой колонке. Переключатель «Активные / История / Все». Счётчики вверху: активных сигналов, сегодня новых, следующая свеча H4 через HH:MM:SS (обратный отсчёт).

Действия: открыть карточку, добавить в вотчлист, «Я вошёл» (создаёт запись в журнале с предзаполненными параметрами), скрыть инструмент, экспорт CSV (Pro+).

Пользователь Free видит сигналы с задержкой (см. тарифы) и размытые цены на свежих сигналах с кнопкой «Открыть доступ».

### 3.5 Карточка сигнала — MVP

- Шапка: инструмент, направление, градация, статус, время создания, версия стратегии, ссылка «Открыть на бирже».
- График (компонент из `packages/charts`, раздел 2A, в урезанном режиме без рисования и настройки индикаторов): свечи H4 с отрисованными зоной входа, стопом, тейками, swing-точками, линией BOS, уровнями PDH/PDL, найденными свечными паттернами на сигнальной свече. Переключатель H4/D1. Текущая цена и линия входа. Маркеры событий (вход, TP1, BE, выход). Кнопка «Открыть в терминале» переносит на 3.17 с сохранением слоёв.
- Блок «Параметры»: вход (рыночный/лимитный), SL, TP1/2/3 с процентами и расстоянием в R и в %, рекомендованная схема частичного закрытия.
- Блок «Обоснование» — генерируется по шаблону из фактов движка, а не свободным текстом: «D1: восходящая структура (HH 04.10, HL 11.10), цена выше EMA50. H4: BOS 23.10 20:00 с закрытием на 0.42 ATR выше уровня, объём 1.6× среднего. Зона: OB 61 240–61 780 совпадает с FVG. Ликвидность: снятие равных минимумов 22.10. Фильтры: ATR в норме (p48), новостей нет, коррелирующий активный сигнал — ETH LONG». Каждый факт кликабелен и подсвечивает элемент на графике.
- Блок «Скоринг»: таблица компонентов с баллами.
- Блок «Калькулятор позиции» (встроенный): риск %, депозит → размер позиции, плечо (для фьючерсов), сумма риска в USDT. Значения берутся из профиля, можно менять.
- Блок «История событий»: лог с таймстемпами.
- Блок «Похожие сигналы в прошлом» (тот же инструмент, та же стратегия) с результатом — v2.
- Действия: «Я вошёл» → журнал, скопировать параметры, поделиться ссылкой (публичная страница с водяным знаком, доступна без логина для закрытых сигналов, активные — только подписчикам), «Напомнить при подходе к входу».

### 3.6 Скринер — v2 (упрощённая версия в MVP)

MVP: таблица всех отслеживаемых инструментов с колонками: bias D1, bias W1, последнее событие H4 (BOS/CHoCH и когда), есть ли активная зона, расстояние до ближайшей зоны в ATR, ATR-режим (перцентиль), изменение за 24 ч, объём 24 ч, funding rate (текущий и перцентиль за 90 дней), изменение OI за 24 ч, ликвидации за 24 ч (лонг/шорт в USDT), бета к BTC. Сортировка и фильтры. Цель — пользователь видит «что близко к сетапу» до появления сигнала.

v2: кастомные фильтры и сохранённые скрины, алерты по условиям скринера («уведомить, когда BTC вернётся в зону»), мини-графики в строке, экспорт.

### 3.7 Вотчлист — MVP

Список инструментов пользователя. Для каждого: цена, изменение, bias, ближайшая зона, активные сигналы. Приоритет уведомлений: сигналы по вотчлисту приходят всегда, остальные — по настройке. Несколько вотчлистов — v2.

### 3.8 Журнал сделок — MVP (базовый), v2 (полный)

MVP:

Отдельная страница и встроенный виджет в карточке. Поля: депозит, риск %, вход, стоп → размер позиции в монетах и USDT, плечо для достижения размера, ликвидационная цена (приблизительно, по формуле биржи, с дисклеймером), прибыль по TP1/2/3 в USDT и %, R:R. Поддержка спота и фьючерсов. Сохранение пресетов. Корректная работа с округлением под lot size биржи (данные из exchangeInfo).

- Привязка через deep link.
- Сообщение о новом сигнале: инструмент, направление, градация, вход, SL, TP1/2/3, R:R, размер позиции под риск пользователя, ссылка на карточку. Формат — моноширинная таблица.
- Сообщения о событиях: вход активирован, TP1 (перевести стоп в BE), TP2, TP3, SL, истёк, отменён.
- Команды: /signals (активные), /stats (сводка за 30 дней), /watchlist, /mute 2h, /settings.
- Для Free — те же сигналы с задержкой; для Pro — мгновенно.
- Канал-витрина (публичный Telegram-канал) с задержкой 24 ч и результатами — маркетинг.

Push (Web Push в PWA, затем нативный): те же события, настраиваемые по типам.
Email: дайджест (ежедневно/еженедельно), важные события аккаунта, отчёт журнала.

Настройки уведомлений: по каналу × по типу события × по градации × по инструментам (все/вотчлист), тихие часы, лимит в сутки.

Что пользователь может сделать: смотреть любой инструмент и таймфрейм, настраивать и сохранять индикаторы и раскладки, рисовать (с синхронизацией между устройствами), ставить алерты, открывать позицию-рисунок и отправлять её в журнал или калькулятор, читать объяснения найденного, делиться снимком. Тарифные лимиты — раздел 4.

Мобильная версия — по 2A.7: портрет и ландшафт, bottom sheet вместо модалок, жесты pinch/pan/long-press/double-tap, 60 fps на целевых устройствах.

## 5. Дизайн: правила «не как у ИИ»

### 5.1 Принцип

Интерфейс — рабочий инструмент. Эталон — терминал Bloomberg, Interactive Brokers TWS, старый Binance, Linear, Stripe Dashboard, газетные финансовые таблицы (FT, WSJ). Критерий: опытный трейдер должен за 3 секунды понять, что перед ним инструмент, а не продающий сайт.

### 5.4 Типографика

- Основной текст: **IBM Plex Sans** (альтернативы: Source Sans 3, Public Sans).
- Цифры, цены, таблицы, код: **IBM Plex Mono** с табличными цифрами (`font-variant-numeric: tabular-nums`). Все цены в одном столбце выравниваются по правому краю и по десятичной точке.
- Заголовки: тот же IBM Plex Sans, вес 600, без разрядки; размер заголовков небольшой (24–28px для h1), интерфейс не кричит.

- Цены показываются с точностью инструмента (из exchangeInfo), без лишних нулей; изменения — со знаком и в процентах с одним знаком после запятой.
- Время — всегда с указанием зоны (UTC / локальная), формат `25.10 16:00 UTC`.

### 5.5 Сетка и плотность

- Контейнер до 1440px, 12-колоночная сетка, отступы 16/24px. Боковая навигация 220px (сворачивается до 56px).
- Таблицы: высота строки 36px, зебра отсутствует, разделители 1px, hover — фон выделения.
- Панели: заголовок 32px с названием слева и действиями справа, без иконок-украшений.
- Пустые состояния — одна строка текста и действие, без иллюстраций.
- Мобильная версия: таблица превращается в плотный список по две строки на запись, не в карточки с большими отступами.

### 5.6 Графики

Никаких градиентных областей под линиями. Для индикаторов — фиксированный набор 6 нейтральных оттенков в токенах (светлая тема: #4A6FA5, #8B6F3E, #6B7F4A, #7A5C7A, #3E7F85, #8A5A44; тёмная: #7FA3D6, #C9A66B, #9DB36F, #B08BB0, #6FB3B8, #C98B72); маркеры паттернов — монохромные глифы. Полные правила для терминала — 2A.9.

### 5.7 Тон текстов

- Коротко, в настоящем времени, без восклицаний.
- Факты и числа вместо прилагательных. «За 90 дней: 61 сигнал, винрейт 47 %, средний R 0.62, просадка 7.3 R».
- Признаём неопределённость: «Система убыточна в периоды затяжного флэта. Худший месяц: март 2025, −6.1 R».
- Обращение на «вы» без заглавной. Никаких «друзья», «трейдеры!».
- Ошибки и пустые состояния — по делу: «Нет активных сигналов. Следующая проверка через 2 ч 14 мин».

### 5.8 Референсы и мудборд словами

- **Bloomberg Terminal**: плотность, моноширинные цифры, функциональная цветовая кодировка, отсутствие декора.
- **Interactive Brokers TWS / Thinkorswim**: таблицы с десятками колонок, живые данные, настройки столбцов.
- **Financial Times (сайт и бумага)**: тёплый бумажный фон, сдержанная типографика, серьёзность.
- **Linear.app**: аккуратность и скорость интерфейса, клавиатурная навигация, тонкие границы — но без их фиолетового.
- **Stripe Dashboard**: ясность таблиц и форм, моноширинные идентификаторы.
- **Старый Binance (2018–2019)** и **Kraken Pro**: биржевой ордербук, компактность.

Чего нет на мудборде: лендингов криптопроектов, 3D-монет, тёмных экранов с фиолетовыми свечениями, фотографий людей с ноутбуками.

## 6. Техническая архитектура

### 6.1 Общая схема

```
Биржи (Binance, Bybit; v2: OKX, Bitget, Hyperliquid) — единый интерфейс ExchangeAdapter
   │ WebSocket kline 1m/4h, aggTrade, forceOrder (ликвидации), markPrice (funding);
   │ REST история, exchangeInfo, openInterestHist, fundingRate, topLongShortRatio
   ▼
[market-data] ─── запись свечей ──► TimescaleDB (hypertable candles)
   │                                  │
   │ событие "свеча H4 закрыта"       │
   ▼                                  ▼
[scheduler] ──► очередь ──► [signal-engine] ── читает свечи, пишет signals, signal_events
                                  │
                                  ▼
                         [tracker] ── слушает 1m/тики, обновляет статусы сигналов, пишет события
                                  │
                                  ▼
                         [notifier] ── очередь ──► Telegram API / Web Push / Email (Postmark/Resend)
                                  
[api] (FastAPI) ◄──── [web] (Next.js) ◄──── браузер / PWA / React Native
      │
      ▼
 Postgres (users, subscriptions, journal, ...), Redis (кэш, pub/sub для живых цен, rate limit)
 
[stats-worker] ── пересчёт агрегатов статистики по расписанию и по событию закрытия сигнала
[backtester] ── отдельный CLI/воркер, те же модули движка, читает историю из TimescaleDB

Модуль графика и анализа (раздел 2A):
[chart-data] ── REST /candles (порции по 500, агрегаты 5m/15m/1h из 1m), WS текущей свечи,
                 серверные индикаторы (Volume Profile, CVD), market_states и сигналы как слои
[pattern-detector] ── на закрытии свечи каждого TF: engine/patterns (свечные), engine/figures (кандидаты фигур)
        │               → patterns, pattern_events; через N свечей → pattern_outcomes; агрегаты → /stats/patterns
        ▼
[ml-inference] ── ранжирование кандидатов фигур (LightGBM/ONNX, CPU), версии из ml_models, shadow-режим
[alerts-worker] ── Node, та же TS-библиотека индикаторов, что на клиенте; проверка алертов по 1m и по закрытию TF
                    → notifier
[llm-gateway] ── факты из API → Claude (Haiku/Sonnet-класс) → постпроверка чисел → кэш Redis 24 ч → ответ;
                  лимиты по тарифу и суточный бюджет
```

### 6.2 Фронтенд

- **Next.js 15 (App Router) + TypeScript**, React Server Components для публичных страниц (лендинг, статистика — SEO), клиентские компоненты для ленты и карточки.
- Состояние и данные: TanStack Query, WebSocket-клиент для живых цен и статусов (через API-гейтвей, не напрямую на биржу).
- Стили: CSS Modules или Tailwind с жёстко заданными токенами (запрет произвольных цветов через ESLint-правило). Компонентная библиотека — своя, на базе Radix Primitives (доступность).
- Графики: TradingView Lightweight Charts **v5** (panes, primitives) внутри собственного пакета `packages/charts` (TypeScript без React: движок слоёв, индикаторы, рисование, жесты, темы) и React-обёртки `packages/charts-react`. Та же библиотека индикаторов исполняется в `alerts-worker` (Node). Тяжёлые расчёты на клиенте — в Web Worker. Выбор движка — 2A.2, ADR-001.
- Таблицы: TanStack Table с виртуализацией.
- i18n: next-intl, ru/en.
- PWA: next-pwa или ручной service worker, Web Push (VAPID), установка на домашний экран, офлайн-кэш последних сигналов.
- Тесты: Vitest + Testing Library (компоненты), Playwright (e2e критических сценариев: регистрация, просмотр сигнала, оплата в sandbox криптопровайдера).

### 6.3 Бэкенд

- **Python 3.12 + FastAPI** для API и воркеров. Pydantic v2 для схем. SQLAlchemy 2 + Alembic для миграций.
- Сигнальный движок — чистый Python-пакет `engine/` без зависимостей от веба: вход — DataFrame свечей, выход — объекты сигналов. Используется одинаково в live, forward и backtest (единая кодовая база — ключевое требование воспроизводимости). Расчёты на pandas/numpy, при необходимости polars.
- Очередь задач: **Celery** или **Dramatiq** с Redis-брокером (или Postgres-очередь через `procrastinate` для простоты). Задачи: генерация сигналов по инструменту, отправка уведомлений, пересчёт статистики, бэктест.
- Планировщик: сервис, который по UTC-часам (00/04/08/12/16/20) ждёт подтверждения закрытия свечи H4 от биржи (событие kline с `x: true` по WebSocket) и только затем запускает движок. Fallback: если через 90 с события нет — REST-запрос последней свечи, сверка времени открытия. Защита от двойного запуска через Redis-lock с ключом `symbol:close_time`.
- Трекер: подписка на kline 1m по всем инструментам с активными сигналами; при каждом закрытии минуты проверка касаний SL/TP; при разрыве соединения — восстановление пропуска через REST 1m-истории.
- Нотифайер: отдельный воркер, идемпотентность по ключу `(user_id, signal_id, event_type)`, ретраи с экспоненциальной задержкой, учёт лимитов Telegram (30 сообщений/с, использовать очередь и батчи).
- API: REST + WebSocket (`/ws` для цен и событий сигналов), версионирование `/v1`. Публичный API для Premium — те же эндпоинты с API-ключом и rate limit.
- `pattern-detector`: модули `engine/patterns` и `engine/figures` в том же пакете `engine/` (общие swing-точки, ATR, единый бэктест); запускается планировщиком на закрытии свечи каждого таймфрейма 15m–1w; пишет `patterns`, `pattern_events`, через N свечей — `pattern_outcomes`. Бэкфилл по истории — отдельная CLI-команда.
- `ml-inference`: Python-сервис с моделями из `ml_models` (LightGBM; CNN — через ONNX Runtime на CPU), версии и shadow-режим; обучение — отдельный пайплайн `ml/` (DVC или MLflow для датасетов, метрик и артефактов), обучение запускается вручную, не в проде.
- `alerts-worker`: Node.js-воркер с `packages/charts/indicators`; алерты по цене — по 1m из трекера; по индикаторам/паттернам — по событиям закрытия свечи и записям `patterns`; идемпотентность по `(alert_id, trigger_time)`.
- `llm-gateway`: единственная точка вызова Claude API (Anthropic SDK), сбор фактов, системные промпты в репозитории с версией, постпроверка чисел, кэш, лимиты по тарифу, суточный бюджет, логирование стоимости по пользователю. Ключ API — только у этого сервиса.
- Аутентификация: собственная на JWT (access 15 мин + refresh в httpOnly cookie) или Auth.js на фронте с бэкенд-проверкой; OAuth Google; Telegram Login с проверкой hash.

### 6.4 Данные

- **PostgreSQL 16 + TimescaleDB** — свечи как hypertable с компрессией старше 30 дней; continuous aggregates для D1/W1 из H4 (или хранение всех трёх таймфреймов отдельно — проще и надёжнее; принимаем хранение отдельно, агрегаты — для проверки).
- **Redis** — кэш последних цен, pub/sub для WebSocket-фанаута, rate limit, locks, сессии бота.
- Объектное хранилище (S3-совместимое: Cloudflare R2 / Backblaze) — скриншоты журнала, экспорты, отчёты бэктестов.
- Историческая загрузка: скрипт загрузки свечей с Binance Data Vision (zip-архивы по месяцам) + REST для догрузки; проверка целостности (отсутствие пропусков по времени, нулевых объёмов).

### 6.5 Мобильное приложение

- Старт: **PWA** (один код с вебом, установка на экран, push). Ограничение: iOS Web Push работает только для установленных PWA с iOS 16.4+.
- v2: **React Native (Expo)** с общими TypeScript-типами API, нативные push (FCM/APNs), биометрия для входа, виджет «активные сигналы». Экраны: лента, карточка, терминал-график (`packages/charts` в WebView с нативными панелями и bottom sheet; запасной план — `react-native-skia`, см. 2A.7), уведомления, журнал, калькулятор, настройки. Оплата: Stripe через веб (в сторах подписки на «контент» — проверить требования Apple к In-App Purchase; возможно, придётся делать IAP — риск, см. раздел 11).

### 6.6 Хостинг и инфраструктура

- Старт: один VPS-кластер (Hetzner, 2–3 машины) с Docker Compose или k3s; либо управляемое: Fly.io / Railway для сервисов + Neon/Timescale Cloud для БД + Upstash Redis. Выбор по бюджету; рекомендуем Hetzner + managed Postgres для простоты и цены (~150–300 USD/мес на старте).
- Фронтенд: Vercel (или self-host Next.js на том же кластере, чтобы не зависеть от лимитов).
- CDN и защита: Cloudflare (DNS, WAF, rate limit, Turnstile вместо капчи).
- Email: Resend или Postmark. Telegram: Bot API через webhook.
- CI/CD: GitHub Actions — линтеры, тесты, сборка образов, деплой в staging по merge в `main`, в production — по тегу.
- Окружения: local (Docker Compose с mock-биржей), staging (реальные данные, sandbox криптопровайдера), production.

### 6.7 Мониторинг и наблюдаемость

- Метрики: Prometheus + Grafana (или Grafana Cloud): задержка от закрытия свечи до публикации сигнала (SLO: p95 < 60 с), задержка данных с бирж, глубина очередей, ошибки уведомлений, доля доставленных Telegram-сообщений; для графика — задержка `/candles` (p95 < 300 мс), задержка срабатывания алертов, время детекции паттернов после закрытия свечи (p95 < 30 с), расход токенов и стоимость LLM в сутки, доля отброшенных постпроверкой ответов LLM, клиентские метрики производительности графика (Sentry Performance).
- Логи: структурированные JSON (structlog), Loki или Better Stack.
- Ошибки: Sentry (фронт и бэк).
- Алерты: нет закрытия свечи в ожидаемое время +2 мин; движок не отработал по > 5 % инструментов; WebSocket биржи отключён > 60 с; очередь уведомлений > 1 000; расхождение между нашими свечами и REST-проверкой.
- Статус-страница публичная (Upptime / Instatus).
- Продуктовая аналитика: PostHog (self-hosted на том же кластере или облако) — события экранов, воронка регистрация → триал → оплата, удержание, без передачи персональных данных сверх user_id; cookie-согласие в ЕС/UK. Нужна с первого дня беты, иначе метрики успеха из раздела 9 измерить нечем.

### 6.8 Безопасность

- Хэширование паролей Argon2id; refresh-токены с ротацией; защита от перебора (rate limit, Turnstile).
- Все секреты в менеджере секретов (Doppler / Infisical / SOPS), не в репозитории.
- API-ключи бирж пользователей (v2, импорт сделок) — только read-only, шифрование на уровне приложения (libsodium) ключом из KMS, предупреждение при вводе ключа с правами торговли.
- Вебхуки криптопровайдера — проверка подписи и повторная сверка статуса платежа по API провайдера (вебхук сам по себе не считается подтверждением); сверка суммы и монеты с инвойсом; защита от повторной обработки по id транзакции.
- Защита от скрейпинга сигналов: водяной знак на публичных карточках, rate limit, задержка для Free, отслеживание массовых выгрузок.
- Регулярные зависимости: Dependabot, `pip-audit`, `npm audit` в CI.
- Резервные копии: ежедневный дамп Postgres с хранением 30 дней, еженедельная проверка восстановления.
- Аудит-лог действий админов и всех изменений статусов стратегий.
- Разделение ролей: `user`, `support`, `admin`, `owner`; смена статуса стратегии — подтверждение двумя `admin`.

## 8. Юридическая часть

Нужна консультация юриста по выбранной юрисдикции до публичного запуска. Ниже — требования к продукту.

1. **Дисклеймер** на лендинге (футер и первый экран), при регистрации (обязательное согласие), в каждой карточке сигнала, в каждом сообщении бота (короткая строка), на странице статистики: «Информация носит образовательный и информационный характер, не является индивидуальной инвестиционной рекомендацией. Торговля криптовалютами и производными инструментами связана с риском потери всех средств. Прошлые результаты не гарантируют будущих».
2. **Запрет на обещания доходности**: в текстах, рассылках, рекламе и реферальных материалах нельзя указывать ожидаемую прибыль в деньгах или процентах как обещание; допускается только историческая статистика с пометкой периода и типа (бэктест/форвард/live) и с указанием просадки рядом. Это правило — пункт чеклиста ревью любого текста. Для паттернов, фигур и текстов, составленных LLM, действуют те же требования плюс запреты 2A.10.6; под каждым сгенерированным текстом — строка «Текст составлен автоматически по данным графика, не является рекомендацией». В политике конфиденциальности указывается, что обезличенные данные графика и вопрос пользователя передаются провайдеру LLM (Anthropic) как субпроцессору.
3. **Условия использования**: сервис — информационный, пользователь принимает решения самостоятельно; ответственность ограничена стоимостью подписки; запрет перепродажи и ретрансляции сигналов; правила возвратов (например, 7 дней для первой оплаты); право блокировать аккаунты за злоупотребления.
4. **Политика конфиденциальности и персональные данные**: GDPR-совместимость (экспорт и удаление данных по запросу, минимизация: не запрашиваем точный депозит без необходимости), cookie-уведомление без «тёмных паттернов», список субпроцессоров (криптоплатёжный провайдер, Telegram, Google, email-провайдер, хостинг, Anthropic). Для РФ-пользователей — отдельная оценка 152-ФЗ (локализация данных) юристом.
5. **Юрисдикции**: география ограничивается по стране регистрации и IP. Ориентир по умолчанию — не предоставлять платные услуги резидентам США (сигналы на фьючерсы могут трактоваться как инвестиционные советы, требующие регистрации CTA/RIA), а также странам под санкциями. Финальный список — от юриста. В ЕС учесть MiCA (режим для криптоуслуг; информационный сервис без хранения активов и исполнения сделок под лицензирование, по предварительной оценке, не попадает — подтвердить у юриста), в UK — правила FCA о продвижении криптоактивов (financial promotions).
6. **Налоги**: при оплате только криптовалютой автоматического расчёта НДС/VAT нет — порядок учёта выручки в крипте, НДС для покупателей из ЕС/UK и отчётность определяет бухгалтер/юрист выбранной юрисдикции до запуска. Это одна из причин выбрать юрисдикцию уже на этапе 0.
7. **Реферальная программа**: выплаты физлицам — налоговые и правовые последствия; на старте начисления только в виде скидок на подписку.
8. **Интеллектуальная собственность и данные**: условия использования данных Binance/Bybit (публичные данные, не ретранслируем сырые котировки третьим лицам); лицензия Lightweight Charts (Apache 2.0, обязательна атрибуция TradingView в интерфейсе).
9. **Маркетинг**: ссылки на биржи с реферальными кодами помечаются как партнёрские.
10. **Возрастное ограничение**: 18+.

Тексты документов пишет юрист; Fable 5 может подготовить черновики по этому разделу, но публикация — только после проверки человеком (см. раздел 10.4).

Исходный расчёт при запуске с полным графиком: **~24 недели** (было ~20 без терминала-графика; график добавляет ~4 недели к критическому пути, так как частично идёт параллельно этапам 2 и 3), при условии, что форвард-тест стартовал к началу этапа 2 и дал ≥ 12 недель наблюдения. Этап 4 с фигурами и ML — ~16 недель вместо 10. Если форвард покажет расхождение с бэктестом — запуск откладывается, а не маскируется. Вариант сокращения: запустить платно без терминала (конец этапа 3, ~20 недель) и выпустить график через месяц — решает заказчик (вопрос 17).

Все сроки выше — оценка при условии, что задачи ставятся без простоев и ревью человека не задерживается. Практика показывает, что такие оценки сбываются редко: закладываем **буфер 25–30 %** (то есть реалистичный горизонт платного запуска — 28–32 недели) и пересматриваем план после этапа 1, когда станут известны результаты бэктеста и реальная скорость работы связки «техлид + Fable 5».

Текущие расходы после запуска при 1 000 платящих — порядка 1 000–2 500 USD/мес, что укладывается в 5–10 % выручки при MRR ≈ 30 000 USD.

## 10. Разработка с Fable 5

### 10.1 Правила репозитория

Моно-репозиторий: `apps/web` (Next.js), `apps/api` (FastAPI), `apps/alerts-worker` (Node), `apps/llm-gateway`, `packages/engine` (Python: движок сигналов, `patterns`, `figures`), `packages/charts` и `packages/charts-react` (TypeScript: график, индикаторы, рисование, жесты), `ml/` (датасеты, обучение, карточки моделей), `packages/shared-types` (OpenAPI → TS), `infra/` (Docker, Terraform/Compose), `docs/` (этот документ, ADR-записи).

**CLAUDE.md** в корне содержит:
- Назначение проекта и ссылка на этот план.
- Команды: установка, запуск, тесты, линт, миграции, бэктест.
- Правила: не менять параметры стратегий без новой версии; не трогать таблицу `signals` UPDATE'ом; все цены — Decimal, не float; время — только UTC в хранении; никаких внешних вызовов из `engine/`; дизайн-токены только из `packages/ui/tokens`; запрещённые слова и паттерны дизайна (раздел 5.2); перед PR — тесты и линт; один PR — одна задача.
- Правила модуля графика и анализа: индикаторы и паттерны считаются только по закрытым свечам (текущая свеча — отдельным помеченным значением); любое изменение правил паттернов — новая `pattern_rules_version`, подтверждённые паттерны не пересчитываются; TS- и Python-реализации индикаторов должны проходить общий golden-набор; Claude API вызывается только из `llm-gateway`, промпты лежат в `apps/llm-gateway/prompts` с версией, в ответах запрещены числа, отсутствующие во входных фактах (постпроверка обязательна), запрещённые формулировки — 2A.10.6; код графика не должен тянуть React в `packages/charts`; в `packages/charts` бюджет кадра проверяется perf-тестом в CI (Playwright + трассировка, порог 16 мс p95 на эмулируемом троттлинге 4×).
- Соглашения: Conventional Commits, ветки `feat/`, `fix/`; PR-шаблон с чеклистом (тесты, миграции, обновление документации, скриншоты для UI).
- Что требует подтверждения человека (раздел 10.4).

**Качество:**
- Python: ruff, mypy (strict для `engine/`), pytest с покрытием ≥ 90 % для `engine/`, ≥ 70 % для API.
- TypeScript: ESLint (с кастомным правилом на запрет произвольных цветов и шрифтов), Prettier, tsc strict, Vitest, Playwright.
- CI (GitHub Actions): линт → типы → юнит-тесты → интеграционные тесты с Postgres/Redis в сервисах → e2e на staging-сборке → сборка образов. Merge в `main` только через PR с зелёным CI и одним ревью человека.
- Pre-commit хуки.
- ADR (Architecture Decision Records) для ключевых решений — Fable 5 пишет черновик, человек утверждает.

### 10.2 Как формулировать задачи для Fable 5

Каждая задача — отдельный промпт (issue) по шаблону:

```
Задача: <что сделать одной фразой>
Контекст: <ссылка на раздел плана, зависимости, что уже есть>
Входные данные: <файлы, схемы, примеры данных, параметры>
Требования: <нумерованный список>
Критерии приёмки: <проверяемые утверждения>
Как проверить: <команды, тесты, ручные шаги>
Ограничения: <что нельзя трогать, что требует согласования>
```

Задачи размером 0.5–2 дня работы. Fable 5 возвращает PR с описанием изменений, результатами тестов и списком того, что осталось неясным. Неясности решает человек до следующей задачи.

| Деньги | Код криптоплатежей, тарифные ограничения, возвраты, реферальные начисления — ревью строка за строкой; ручной прогон в test mode и одна боевая оплата | Техлид |
| Юридические тексты | Дисклеймеры, оферта, политика, тексты лендинга и рассылок, тексты бота — Fable 5 пишет черновик, юрист утверждает | Юрист + заказчик |
| Безопасность | Аутентификация, хранение ключей, вебхуки, права админов | Техлид + внешний аудит на этапе 5 |
| Дизайн | Каждый новый экран — чеклист раздела 5 | Дизайнер/заказчик |
| Данные | Целостность истории свечей, корректность статистики (ручная сверка 20 сделок) | Техлид |
| Инфраструктура | Доступы, секреты, бэкапы, восстановление | Техлид |
| Правила паттернов | Каждое правило свечного паттерна и шаблон фигуры — визуальная проверка на 20 реальных примерах на тип; любое изменение допусков — новая версия правил после ревью | Заказчик/техлид с торговым опытом |
| Разметка и модель | Разметка фигур выполняется только людьми (не Fable 5 и не LLM); kappa ≥ 0.6; метрики модели (precision/recall по типам, PR-AUC), SHAP-отчёт и отчёт shadow-режима читает и подписывает человек; выпуск модели в live — два админа | Заказчик + техлид |
| LLM-тексты | Системные промпты и любые их изменения; выборочная проверка 30–50 ответов на каждой новой версии промпта или модели на отсутствие рекомендаций, прогнозов и «чужих» чисел; суточный бюджет | Техлид + юрист (формулировки) |
| Производительность графика | Приёмка на реальных целевых телефонах (не только эмулятор) по чеклисту жестов 2A.7 | Техлид/дизайнер |

Fable 5 не получает боевых ключей платёжного провайдера, кошельков, бирж и доступа к production-БД. Деплой в production — человек.

## 11. Риски и их снижение

| Риск | Вероятность | Влияние | Снижение |
|---|---|---|---|
| Стратегия не проходит бэктест или форвард расходится с бэктестом | Средняя | Критическое | Этап 1 до вложений в сайт; честные пороги; запасные стратегии; готовность отложить запуск |
| Период убытков после запуска → отток и негатив | Высокая (неизбежны серии) | Высокое | Публично показываем худшие периоды заранее; обучение про R и просадку; уведомление «система в просадке, это нормально по бэктесту до X R» |
| Юридические претензии (инвестиционные советы) | Средняя | Критическое | Юрист до запуска, гео-ограничения, дисклеймеры, отсутствие персональных рекомендаций и автоисполнения в MVP |
| Утечка/перепродажа сигналов | Высокая | Среднее | Задержка для Free, водяные знаки, ограничение экспорта, отслеживание аномалий, ценность в журнале/статистике/боте, а не только в цифрах |
| Неполнота бесплатных деривативных данных: стрим ликвидаций Binance `forceOrder` отдаёт не больше одной ликвидации в секунду на символ, история ликвидаций и long/short ratio через REST ограничена ~30 днями | Высокая | Среднее | Ликвидации используем как относительный индикатор (всплеск к своему среднему), а не как точный объём; копим собственную историю с первого дня этапа 0; бэктест фильтров ликвидаций — только на периоде, где данные есть; карта плотности ликвидаций — по платному источнику (Coinglass API) в v2 |
| Оплата только криптовалютой режет конверсию: часть аудитории (особенно сегмент A и D) не умеет или не хочет платить криптой; нет автопродления — выше отток на границе периода | Высокая | Высокое | Пошаговая инструкция оплаты с видео и поддержкой в боте; скидка за 3 и 12 месяцев; напоминания за 7/3/0 дней и оплата заранее; измерять долю брошенных инвойсов; если конверсия триал → оплата < 7 % два месяца подряд — подключать карты (вопрос 9) |
| Криптопровайдер заблокирует аккаунт мерчанта или потребует KYC/лицензию; прямой приём на свои адреса создаёт налоговые и AML-риски | Средняя | Критическое | Выбрать провайдера с понятными правилами для инфо-сервисов, пройти проверку на этапе 0; держать второго провайдера подключённым «на холодную»; юрист — по AML и учёту крипто-выручки в выбранной юрисдикции |
| Отказ или изменение API бирж | Средняя | Высокое | Два источника (Binance + Bybit), абстракция провайдера, алерты, REST-fallback |
| Задержка публикации сигнала (> 60 с) | Средняя | Среднее | SLO, мониторинг, предрасчёт зон до закрытия свечи, финальная проверка по закрытию |
| Ошибка в коде движка на проде, разошедшаяся с бэктестом | Средняя | Высокое | Единая кодовая база live/backtest, `replay()` в CI, ежедневная сверка форвард-сигналов с офлайн-пересчётом |
| Apple требует In-App Purchase для подписки | Высокая | Среднее | Исследовать на этапе 4; вариант «только вход, покупка на сайте» (reader-app) или IAP с ценой +30 % |
| Блокировки Telegram в отдельных странах | Средняя | Среднее | Push и email как дублирующие каналы |
| Зависимость от одного разработчика-ИИ без ревью | Средняя | Высокое | Обязательные ревью человека по 10.4; тесты; маленькие PR |
| Дизайн всё-таки «как у ИИ» | Средняя | Среднее | Дизайн-система в коде с запретами, ESLint-правила, чеклист перед каждым экраном, дизайнер-человек на этапе 2 |
| Низкая конверсия Free → Pro | Средняя | Высокое | A/B задержки для Free (12 ч vs 24 ч), триал, отчёт «что вы упустили» |
| Переобучение параметров (curve fitting) | Средняя | Критическое | Walk-forward, запрет изменений без новой версии и форварда, минимальное число параметров |
| Рост стоимости инфраструктуры | Низкая | Низкое | Компрессия Timescale, кэш, лимиты API |
| Ложные паттерны и фигуры: пользователи воспринимают отметки как сигналы, торгуют по ним и винят сервис; алгоритм находит «фигуры» в шуме | Высокая | Высокое | Разделение в UI «паттерн ≠ сигнал»; показ исторической отработки с n и CI рядом с каждой отметкой; порог по precision, а не recall; статус «формируется» только для Premium и пунктиром; shadow-режим моделей; жалоба «ложная фигура» одним тапом с учётом в метриках; запрещённые формулировки (2A.10.6) |
| Стоимость LLM растёт быстрее выручки (злоупотребление лимитами, рост базы Pro) | Средняя | Среднее | Кэш объяснений на всех пользователей; лимиты по тарифу; суточный бюджет с деградацией в шаблонные тексты; Haiku-класс по умолчанию; учёт стоимости по пользователю и отключение аномальных; цены пересматриваются по факту через 2 месяца |
| LLM выдаёт некорректный текст (выдуманные уровни, рекомендации) несмотря на промпт | Средняя | Высокое | Постпроверка чисел с отбросом ответа; запрет глаголов-рекомендаций словарём; выборочное ревью человеком каждой версии промпта; дисклеймер под каждым текстом; логи для разбора жалоб |
| Производительность графика на слабых телефонах (Android до 2020 года, 2–3 ГБ ОЗУ): лаги, перегрев, вылеты WebView | Высокая | Среднее | Бюджет кадра и perf-тесты в CI; лимит свечей в памяти; culling; деградация детализации; «лёгкий режим» (без Heikin Ashi, не более 3 индикаторов, без паттернов в видимом диапазоне > 1 000 свечей) включается автоматически по измеренному fps; список поддерживаемых устройств публичен |
| Объём и качество ручной разметки фигур недооценены (60–80 часов людей, расхождения разметчиков) | Средняя | Среднее | Начать разметку в этапе 2B параллельно разработке; оплатить внешних разметчиков-трейдеров; если kappa < 0.6 — упростить таксономию (объединить типы) до приемлемой согласованности; фигуры могут выйти позже без блокировки остального этапа 4 |
| Зависимость от Lightweight Charts (смена API между мажорными версиями, ограничения примитивов) | Низкая | Среднее | Собственный слой абстракции в `packages/charts` (рендер за интерфейсом); пин версии; KLineChart как проверенный запасной вариант по ADR-001 |

10. Реферальные выплаты деньгами или только скидками?
11. Автоисполнение сделок на бирже — нужно ли в принципе (v3), или сервис остаётся информационным?
12. Публичность правил: допускается ли полное раскрытие логики (как здесь) или параметры скрываем?
13. Дизайнер-человек на этапе 2: есть ли, или дизайн делает Fable 5 по разделу 5 с вашим ревью?
14. Телеграм-канал-витрина: публикуем ли все сигналы с задержкой 24 ч (маркетинг) или это снизит ценность подписки?

16. Терминал-график: согласны с выбором Lightweight Charts v5 + свои слои (2A.2), или есть предпочтение по движку? Готовы ли принять, что в MVP график уступает TradingView по количеству функций?
17. Сроки: публичный платный запуск вместе с графиком (~24 недели) или сначала без графика (~20 недель), график — через месяц после?
18. Какие таймфреймы действительно нужны пользователям ниже 1h? Можно ли ограничиться 15m как минимальным (экономит трафик и упрощает детектор)?
19. Список целевых устройств для приёмки мобильной версии (3–4 модели iPhone/Android, включая слабый Android)?
20. Разметка графических фигур: кто со стороны заказчика готов размечать (60–80 часов суммарно на 2–3 человека) или привлекаем платных разметчиков-трейдеров?
21. LLM: подтверждаете использование Claude API (данные графика уходят к внешнему провайдеру, персональные данные не передаются)? Нужен ли вариант без LLM вообще (только шаблонные тексты)?
22. Приоритет фигур: все 10 типов сразу или начать с 4 самых частых (двойная вершина/дно, флаг, треугольник, голова-плечи)?
23. Публичность статистики отработки паттернов: показываем всем без логина (как статистику сигналов) или только зарегистрированным?
24. (Решено 25.10.2026: выпускаем ядро первым, см. 3.19.) Объём первого релиза: в MVP сейчас заложено много (лента, карточка, статистика, журнал, скринер, калькулятор, вотчлист, график с 10+ индикаторами, рисование, алерты, паттерны, LLM, бот, оплата). Готовы ли сократить первый публичный релиз до ядра — лента + карточка + статистика + график с базовыми индикаторами и слоями системы + бот + оплата — а журнал, скринер, рисование, алерты и паттерны выпускать по одному в следующие 2–3 месяца? Это снижает срок до запуска и риск, что всё выйдет сырым одновременно.

## Приложение A. Глоссарий

Короткие определения терминов, которые используются в документе и будут встречаться в интерфейсе. Пригодится при согласовании плана и для раздела «Обучение» в продукте.

| Термин | Значение |
|---|---|
| H4, D1, W1, 1m | Таймфреймы: одна свеча = 4 часа, 1 день, 1 неделя, 1 минута |
| OHLCV | Открытие, максимум, минимум, закрытие и объём свечи |
| Perpetual (бессрочный фьючерс), USDT-M | Контракт без даты экспирации с расчётами в USDT; позволяет шорт и плечо |
| Funding rate (ставка финансирования) | Периодический платёж между лонгами и шортами на perpetual-рынке; показывает, в какую сторону перекошена толпа |
| Open interest (OI, открытый интерес) | Суммарный объём открытых позиций по контракту |
| Ликвидации | Принудительные закрытия позиций с плечом; их всплески показывают, где «выбило» участников |
| Long/short ratio | Доля лонгов и шортов среди трейдеров биржи (глобально или среди топ-трейдеров) |
| Swing high / swing low | Локальный максимум/минимум, подтверждённый свечами по бокам |
| HH / HL / LH / LL | Higher high, higher low, lower high, lower low — последовательность экстремумов, по которой определяется тренд |
| BOS (break of structure) | Закрытие свечи за предыдущим swing-экстремумом по тренду — подтверждение продолжения |
| CHoCH (change of character) | Первое закрытие против текущей структуры — признак возможной смены направления |
| Order block (OB) | Последняя контртрендовая свеча перед импульсом, пробившим структуру; используется как зона для входа на возврате цены |
| Зона спроса / предложения (S/D) | Область консолидации перед сильным импульсом |
| FVG (fair value gap) | Ценовой разрыв между первой и третьей свечой трёхсвечного импульса |
| Ликвидность, sweep | Скопления стопов за равными максимумами/минимумами; sweep — прокол такого уровня хвостом с возвратом |
| PDH/PDL, PWH/PWL | Максимум/минимум предыдущего дня и предыдущей недели |
| ATR | Average true range — средний диапазон свечи; мера волатильности, в которой измеряются стопы и допуски |
| EMA / SMA | Экспоненциальная / простая скользящая средняя |
| R, R:R | R — величина риска в сделке (расстояние от входа до стопа); результат сделки измеряется в R; R:R — отношение потенциальной прибыли к риску |
| TP1/TP2/TP3, SL, BE | Уровни фиксации прибыли, стоп-лосс, безубыток (стоп переносится на цену входа) |
| Винрейт, профит-фактор, expectancy, просадка | Доля прибыльных сделок; отношение суммы прибылей к сумме убытков; средний результат сделки в R; максимальное снижение капитала от пика |
| Бэктест / форвард-тест / live | Проверка стратегии на истории / на живых данных без публикации / в боевом режиме для пользователей |
| Walk-forward | Подбор параметров на одном периоде истории и проверка на следующем, чтобы избежать подгонки |
| No repaint (без перерисовки) | Сигнал или отметка, рассчитанные по закрытым свечам и не меняющиеся задним числом |
| Скоринг, градация A/B/C | Балльная оценка качества сетапа и её группы |
| Свечной паттерн / графическая фигура | Комбинация 1–3 свечей (поглощение, пин-бар) / геометрическая формация из многих свечей (голова-плечи, треугольник) |
| Precision / recall / PR-AUC / kappa | Метрики ML-модели: доля верных среди найденных / доля найденных среди всех настоящих / интегральная метрика / согласованность разметчиков |
| Shadow-режим | Модель работает и пишет результаты, но пользователям они не показываются |
| LLM | Большая языковая модель (здесь — Claude), используется только для текста по готовым фактам |
| PWA | Веб-приложение, устанавливаемое на телефон из браузера, с push-уведомлениями |
| MRR, churn, LTV/CAC | Месячная повторяющаяся выручка; отток подписчиков; отношение дохода с клиента к стоимости его привлечения |
