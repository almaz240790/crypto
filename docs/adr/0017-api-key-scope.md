# ADR-0017. Что открывает API-ключ для чтения

Статус: принято. Дата: 2026-11-13. Решение принято Fable по делегированию (ADR-0012), владелец: «Делай по твоему».
План 3.10 («API-ключ для чтения истории — Premium»), 6.3.

## Контекст

После PR #167 заголовок `X-API-Key` понимают `auth.current_user` и `auth.optional_user`. Так ключ стал работать
на всех GET за `current_user`, а не только на данных, которые обещает /api-docs: скрипт с ключом читал выгрузку
данных аккаунта (`/v1/me/export.json`: профиль, почта, журнал), список ключей, сессии и устройства, платежи,
подключённые входы, состояние 2FA. Ключ живёт в скриптах и таблицах и утекает чаще пароля, поэтому он не должен
давать больше, чем нужно для чтения рыночных данных.

Пример в настройках (`curl … /v1/signals?tab=all`) был неверным трижды: у `/v1/signals` нет параметра `tab`,
адрес — домен сайта, а прокси сайта (`/v1/*` на www) заголовок `X-API-Key` не передаёт (ответ гостя), ключ обрезан.

## Варианты

1. Отдельные «личные» зависимости без ключа для каждого личного эндпоинта — список запрещённого; новый
   эндпоинт за `current_user` снова открыт ключу, если о нём забыли.
2. Закрытый список разрешённого в одном месте, сверенный с /api-docs тестом; всё остальное по ключу — 403.

## Решение

Вариант 2.
- Ключ открывает только GET эндпоинтов со страницы /api-docs: сигналы (лента, карточка, свечи сигнала),
  статистика (сводка, сделки, CSV, паттерны, фигуры), график (свечи, слои, паттерны, фигуры, производные),
  скринер и его CSV, инструменты, цены, журнал владельца ключа и его аналитика, алерты владельца.
  Список — `apikeys.KEY_ENDPOINTS`; страница берёт свой из `apps/web/src/lib/apiDocs.ts`. Тесты с обеих
  сторон (`test_apikeys.py`, `apiDocs.test.ts`) требуют, чтобы списки совпадали, а каждый пункт был
  действующим GET-эндпоинтом.
- Проверка `apikeys.key_scope` — зависимость всего приложения (`app.main`): запрос с `X-API-Key` не GET —
  403 «API-ключ даёт только чтение», эндпоинт не из списка — 403 «API-ключ не даёт доступа к этому разделу
  (список — на странице /api-docs)». Сравнивается шаблон пути, выбранный FastAPI (`/v1/signals/{public_id}`),
  а не адрес запроса. Новый эндпоинт закрыт ключу сам; тест обходит все GET из OpenAPI.
- Отказ за пределами списка — до проверки самого ключа: неверный ключ там тоже получает 403, запрос не
  считается в лимите ключа. На эндпоинтах из списка всё как раньше (401/403 тарифа/429).
- `auth._api_key_user` вызывает ту же проверку: пользователь по ключу не появляется за пределами списка,
  даже если роутер подключён к приложению без общей зависимости.
- Админка по ключу — 403 этого же правила (было 401 «Нужен вход»; ключ админку не открывал и раньше,
  ADR-0011). Сокет `/v1/ws` ключ не читает (вход — токеном в адресе), заголовок там ни на что не влияет.
- Открытые данные, которых нет в /api-docs (`/v1/signals/summary`, `/v1/signals/{id}/analysis`,
  `/v1/strategies`, `/v1/stats/runs`), а также `/v1/journal/export.csv` и `/v1/alerts/triggers` по ключу
  закрыты. Открыть — добавить в оба списка (документация и сервер) одним изменением.
- Сайт (токен Bearer) не меняется: личные разделы по токену — как раньше.
- Пример в настройках строится `apiKeyExample()`: адрес API (`https://api.platformsol.com`), ключ целиком,
  `GET /v1/signals?status=open&limit=50` — параметры из документации (тест сверяет).

## Последствия

- Утёкший ключ даёт только то, что владелец Premium и так видит в документации; профиль, почта, сессии,
  ключи, платежи и выгрузка данных — только по входу на сайте.
- Каждый новый эндпоинт для скриптов требует строки в двух списках и в /api-docs — это намеренно.
- Пересмотреть, если появятся ключи с разными правами (например, отдельный ключ для журнала).
