# ADR-0004: воркер алертов на Python, а не на Node

Статус: принято (2026-10-27). Задача 2B.13, план 2A.6 и раздел 6.

## Контекст

План (раздел 6) предлагал `alerts-worker` на Node.js с библиотекой индикаторов `packages/charts`,
чтобы использовать тот же код, что и клиент. К моменту 2B.13 все воркеры (market-data, scheduler,
tracker, notifier, pattern-detector) — Python в `apps/api`, с общими моделями БД, доставкой
уведомлений (`app/notify.py`, `app/push.py`) и движком `engine/`. Индикаторы TS и Python проходят
общий golden-набор с точностью 1e-8 (2B.3), поэтому результат одинаков.

## Решение

`app.workers.alerts` на Python: подписка на `candles.closed`, проверка условий функциями
`app/alerts.py` (цена по 1m, индикаторы/зоны/структура по закрытию свечи TF, паттерны по новым
записям `patterns`), запись в `alert_triggers` с уникальностью `(alert_id, triggered_at)`, доставка
через существующие push/email с настройками пользователя (тихие часы, дневной лимит).

## Последствия

- Один язык и одна кодовая база для всех воркеров; нет дублирования доставки и моделей.
- Расчёт индикаторов — `engine/indicators.py` (эталон для TS), расхождений с клиентом нет.
- Алерты по рисункам (v2) при необходимости потребуют геометрии из `packages/charts` — это
  отдельное решение; при появлении Node-воркера он сможет жить рядом.

## Доставка через уведомитель (дополнение, 2026-11-10)

### Контекст

На Railway у сервиса `alerts` есть `RESEND_API_KEY` и `MAIL_FROM`, но нет `VAPID_*` и `FRONTEND_URL`; ключи
Web Push есть только у уведомителя (`notifier`). Push по алертам молча пропускался, ссылки в письмах вели на
`http://localhost:3000`. Переменные на Railway Fable менять не может — недостающие настройки заменяются кодом
(ADR-0012, ADR-0002 «Дополнение»).

### Решение

- Исходящая очередь — сами строки `alert_triggers`, без новой таблицы и без миграции. Служебная отметка
  `details.delivery`: `status` (`queued` / `sent` / `suppressed` / `expired` / `failed`), `attempts`, `retry_at`,
  `error`, `reason`, `push_done` / `mail_done`, `mail_skipped` / `mail_refused`. В API она не отдаётся
  (`trigger_dict`).
- Воркер пишет срабатывание со `status = queued` в той же транзакции, что и проверку. Сам доставляет, только если
  у процесса есть и ключ почты, и ключи Web Push (локальная разработка); ошибка — строка остаётся в очереди.
- Очередь разбирает уведомитель (`app.alerts.deliver_batch`, задача `alerts_loop`): раз в 15 с и сразу по
  сообщению воркера в Redis-канал `alerts.triggered` (сообщение не дошло — сработает опрос). Строка берётся
  `FOR UPDATE SKIP LOCKED` и перепроверяется под блокировкой, каждое срабатывание — в своей транзакции. Выборка
  была полной (200 строк) и экземпляр что-то обработал — следующий проход сразу, без паузы: всплеск срабатываний
  не ждёт опроса, даже когда часть строк забрал второй уведомитель или они ждут повтора.
- Отказ почты разбирается по ответу Resend, а не по одному коду. Постоянный — только 400/422 об адресе
  получателя (поле `to`): письмо больше не пробуется (`mail_refused`), но push это не отменяет — упавший в той же
  попытке или ждущий ключей push уходит на повторе. Push дошёл — срабатывание доставлено (`sent`, `notified`);
  push пользователь не выбрал — `failed` сразу. Неверный ключ, `MAIL_FROM`, пропущенное поле, лимит, сбой провайдера и
  сеть касаются всех писем (`provider_wide`): письмо повторяется до суток (пауза 30 с × 2ⁿ, не больше 8 минут),
  после исправления настроек оно уйдёт. Прочие ошибки (сбой push, данные) — до 6 попыток, затем `failed`. После
  такого отказа почты до конца прохода письма не отправляются, а ждут 30 с: при таймаутах сети проход не
  растягивается на 15 с × длину очереди, push по остальным срабатываниям уходит сразу. Срабатывание старше
  суток не доставляется (`expired`; если какой-то канал уже ушёл — `notified`). Push, доставленный позже
  5 минут после срабатывания, содержит время срабатывания.
- Каналы независимы: сбой push не мешает письму и наоборот, повтор шлёт только недоставленный канал
  (`push_done` / `mail_done`). Письмо, ушедшее в попытке, где упал push, засчитывается в дневной лимит при учёте
  ошибки (сама попытка откатывается).
- Второй отправки нет: письмо уходит с ключом идемпотентности Resend `alert-trigger-{id}`, push — с `tag`
  `alert-{id}` (повтор заменяет уведомление на устройстве). Письмо, которое Resend не принял (любой отказ, кроме
  409 по ключу — «уже отправлено»), не отмечается доставленным.
- В production каналы проверяются по отдельности (`channels_ready`). Нет ключа канала — он ждёт (`waiting`,
  повторная проверка через 10 минут, попытки не засчитываются), а другой канал уходит: без `VAPID_*` у
  уведомителя письмо всё равно доставляется, push ждёт ключей до суток. Без ключей обоих каналов очередь не
  трогается.
- Тихие часы и дневной лимит решаются один раз — пока ни один канал не ушёл; срабатывание, по которому что-то
  уже доставлено, повтор не подавляет. Только письмо на повторе снова сверяется с лимитом: его могли исчерпать
  другие срабатывания (`mail_skipped`). Строка настроек уведомлений берётся под блокировкой — два уведомителя
  бок о бок лимит не превышают. Каналы и отписка («Отписаться от писем» выключает и письма алертов) проверяются
  на момент доставки, тексты в обоих путях одни (`notify_trigger`).

### Выкладка без простоя

- Прежний воркер и новый уведомитель: прежний воркер доставляет сам, как раньше (письмо — да, push — нет), и
  отметку не ставит; уведомитель такие строки не трогает — второго письма нет.
- Новый воркер и прежний уведомитель: строки ждут в очереди; новый уведомитель после старта доставляет их один
  раз (до суток).
- Два новых уведомителя: `SKIP LOCKED` и ключ идемпотентности — каждое срабатывание доставляется один раз,
  дневной лимит общий (блокировка строки настроек).
- Уведомитель продолжает доставку алертов при перезапуске или недоступности Redis: обращения основного цикла к
  Redis не роняют процесс, а упавший цикл перезапускается через 5 с, не трогая доставку (ей нужен только
  PostgreSQL).
- Воркер алертов после перезапуска Redis подписывается на `candles.closed` снова (через 5 с), а цикл паттернов
  и heartbeat продолжает работу. Раньше обе задачи на обрыве молча завершались: процесс жил, алерты больше не
  срабатывали, и платформа его не перезапускала. Свечи, закрытые, пока Redis лежит, воркер не увидит (pub/sub
  без хранения) — как и раньше.
- Отказ почты или сбой сети при доставке (почты или push-сервиса) пишется в лог предупреждением с причиной, без
  трассировки: при неверном `MAIL_FROM` или недоступной почте такая строка идёт на каждую попытку.

### Push-сервис и зависшая отправка

Очередь разбирается по порядку, поэтому одна зависшая отправка держит доставку всем пользователям. Раньше так и
было: pywebpush шлёт запрос без таймаута, а адрес подписки API принимал любой. Достаточно было указать свой
сервер, который принимает соединение и молчит, и создать алерт.

- Запрос к push-сервису ограничен 10 с (`app.push.PUSH_TIMEOUT`), письмо в Resend — 15 с.
- Адрес подписки — только https на push-сервисах браузеров (`app.push.PUSH_HOSTS`: `fcm.googleapis.com`,
  `android.googleapis.com`, `*.push.services.mozilla.com`, `*.notify.windows.com`, `*.push.apple.com`), без
  нестандартного порта и логина. `POST /v1/me/push` с другим адресом отвечает 400 «push в этом браузере не
  поддерживается». На подписки, записанные раньше с другим адресом, push не шлётся, но они не удаляются: если
  это настоящий push-сервис, которого нет в списке, достаточно добавить его в `PUSH_HOSTS`. Заодно API и
  уведомитель больше не шлют запросы на внутренние адреса сети хостинга.
- У доставки свой heartbeat в Redis (`alert_delivery:heartbeat`): время, когда очередь последний раз двигалась.
  Пока проход идёт, он пишется раз в 10 с, но со временем последнего движения, а не текущим, так что зависшая
  отправка его не обновляет. Монитор показывает компонент «Уведомления» по худшему из этого heartbeat и heartbeat
  основного цикла (те же пороги: 2 и 10 минут). Ключа нет (уведомитель прежней версии при выкладке, Redis
  только что поднялся пустым) — судит по основному. Проход стоит на одном срабатывании дольше минуты —
  предупреждение в логе уведомителя.

Все три варианта и перезапуск Redis проверены запуском самих сервисов с переменными, как на Railway (описание
PR).

### Последствия

- Push по алертам приходит, хотя у сервиса `alerts` нет ключей Web Push. Задержка — около секунды (сообщение
  Redis), без сообщения — до 15 с.
- Уведомитель отвечает и за алерты: пока он не работает, срабатывания копятся в БД (до суток) и уходят после
  старта с пометкой времени.
- Очередь выбирается запросом по `jsonb` без индекса. Если `alert_triggers` вырастет до десятков тысяч строк,
  нужен частичный индекс по `details->'delivery'->>'status'` (отдельная миграция).
