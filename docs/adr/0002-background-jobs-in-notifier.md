# ADR-0002. Монитор и пересчёт снимков статистики живут в процессе `notifier`

Дата: 2026-10-25. Статус: принято.

## Контекст

План (раздел 6) описывает `stats-worker` и мониторинг как отдельные компоненты. На Railway каждый
сервис — отдельный контейнер с отдельной оплатой и отдельной точкой отказа. Пересчёт снимков
статистики занимает доли секунды (сотни сделок), прогон монитора — несколько запросов к Redis и БД.

## Решение

- Воркер `apps/api/app/workers/notifier.py` раз в 30 с читает новые сигналы и события, и в том же цикле:
  - раз в 60 с запускает монитор (`app/monitor.py`: инциденты, алерты владельцам, кэш `monitor:status`);
  - раз в 10 мин и сразу после события закрытия сигнала пересчитывает снимки (`app/snapshots.py`);
  - при старте и раз в час проверяет порядок монет по капитализации (`app/coin_rank.py`): если
    сохранённому в Redis (`coins:rank`) больше суток — забирает CoinGecko `/coins/markets` (две
    страницы и наши монеты по id); сбой оставляет прежний порядок и не останавливает цикл, наша
    монета, пропавшая из ответа, остаётся на прежнем месте с предупреждением в логе (план 6.4).
- Логика остаётся в отдельных модулях с чистыми функциями (`monitor.evaluate`, `snapshots.build`),
  а `app/workers/stats.py` умеет работать самостоятельным сервисом (`--once` или цикл), если
  статистика станет тяжёлой. Разнесение по сервисам — смена команды запуска, не кода.
- `GET /status` и `GET /v1/stats` читают готовый результат (Redis / таблица `stats_snapshots`),
  а при его отсутствии считают на месте, не отправляя алертов.

## Последствия

- Плюс: один контейнер меньше, один heartbeat (`notifier:heartbeat`) покрывает три задачи.
- Минус: падение уведомителя останавливает и монитор — но об этом скажет сам `/status`
  (компонент «Уведомления» по heartbeat) и алерт по e-mail не придёт. Компенсация: внешний
  аптайм-чекер на `GET /status` (поле `status`), настраивается владельцем.
- Минус: пересчёт снимков и рассылка писем делят один поток — при росте нагрузки вынести
  `stats` в отдельный сервис (готово к этому).

## Дополнение (2026-11-10): переменные, которых нет у сервисов на хостинге

### Контекст

Переменные сервисов на Railway (имена): API — `FRONTEND_URL`, `OWNER_EMAILS`, `RESEND_API_KEY`, `MAIL_FROM`,
`VAPID_*`, `API_PUBLIC_URL`; `notifier` — `RESEND_API_KEY`, `MAIL_FROM`, `VAPID_*`, `FRONTEND_URL`, без
`OWNER_EMAILS`; `alerts` — `RESEND_API_KEY`, `MAIL_FROM`, без `VAPID_*` и `FRONTEND_URL`; `digest` (cron,
`scripts/digest.py`) — `FRONTEND_URL`, `MAIL_FROM`, без `RESEND_API_KEY`. Из-за этого письма об инцидентах не
уходили никому, ссылки в письмах алертов вели на localhost, push по алертам не отправлялся, а cron-сервис
`digest` «отправлял» дайджест в лог и отмечал его отправленным. Менять переменные Fable не может (ADR-0012).

### Решение: код вместо настроек

- Production — это `APP_ENV=production`; если `APP_ENV` не задан вовсе — `RAILWAY_ENVIRONMENT_NAME=production`
  (Railway задаёт её каждому сервису сам).
- `FRONTEND_URL` в production по умолчанию `https://platformsol.com`, в лог — предупреждение; заданный адрес на
  localhost остаётся, но с предупреждением. `API_PUBLIC_URL` не подставляется: адрес API нигде не зафиксирован,
  а нужен он только API (вебхук оплаты), у которого переменная есть. При включённой оплате и локальном адресе —
  предупреждение.
- Письма об инцидентах (монитор в уведомителе) получают `OWNER_EMAILS` этого процесса и активные пользователи с
  ролью `owner` и подтверждённым адресом из БД. Два уведомителя бок о бок (выкладка) инциденты не дублируют:
  монитор берёт advisory-блокировку на транзакцию. Инциденты фиксируются до писем, письма — во второй
  транзакции под той же блокировкой, в строгом режиме и с ключом идемпотентности (инцидент, очередное
  оповещение, адресат). Таймаут или отказ провайдера не роняет прогон: отправленные отмечаются, остальные ждут
  следующего прогона через минуту, повтор того же письма Resend не задвоит.
- Отказ Resend разбирается по ответу: постоянный (повтор не поможет) — только ошибка в адресе получателя.
  Неверный ключ или `MAIL_FROM` (400/422) касается всех писем: проход дайджестов прерывается, день не
  отмечается, повтор — через 15 минут.
- Ссылка «Отписаться от писем» выключает все рассылки по email: дайджест, сигналы, события и письма алертов.
- Перезапуск или недоступность Redis не роняет уведомитель: курсоры живут в памяти, дайджесты ждут аренды в
  Redis, heartbeat пишется, когда Redis вернётся; упавший цикл перезапускается через 5 с, остальные работают.
- Дайджесты и отчёт по журналу шлёт уведомитель — у него есть ключ почты. В production процесс без ключа
  рассылку пропускает и ничего не отмечает (`app.notify.mail_ready`); cron-сервис `digest` теперь ничего не делает.
  Отметка в `notification_log` пишется до письма и фиксируется после него: параллельный проход ждёт её и
  пропускает адрес. Письмо уходит с ключом идемпотентности. Отказ провайдера отметку откатывает; временный
  прерывает проход, и уведомитель повторяет его через 15 минут. Отметка «дайджесты за дату отправлены» в Redis
  до прохода ставится на 15 минут (аренда), на трое суток — только после успешного прохода.
- Доставка алертов — ADR-0004, «Доставка через уведомитель».

### Последствия

- Сервисы работают с теми переменными, что есть. Cron-сервис `digest` можно выключить: без ключа почты он
  ничего не делает и ничему не мешает.
- Другой адрес сайта задаётся переменной `FRONTEND_URL` у всех сервисов.
