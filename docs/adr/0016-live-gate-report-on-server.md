# ADR-0016. Отчёт «готовность к live» строит сервер раз в неделю, админка его показывает

Статус: принято. Дата: 2026-11-12. Решение принято Fable по делегированию (ADR-0012).

## Контекст

Задача 9 пакета «Сигналы» дала скрипт `scripts/live_gate_report.py`: форвард версии против бэктеста той же версии
на том же списке инструментов и таблица критериев плана. По плану 10.4 решение о выпуске в live принимает владелец
по этому отчёту. Но форвард-строки есть только в базе production, а у Fable и Claude доступа к ней нет
(CLAUDE.md). Владелец сам ничего запускать не будет (ADR-0012). Значит, отчёт должен строиться там, где данные
есть, — на сервере, и быть виден владельцу без командной строки.

Отчёт тяжёлый: бэктест 59 пар за 4,4 года идёт десятки минут и читает много свечей и деривативов.

## Варианты

1. Человек запускает скрипт на production вручную. Минус: человека, который это сделает, нет.
2. Отдельный сервис Railway по расписанию. Минус: новый сервис настраивает человек в Railway.
3. Эндпоинт админки, который строит отчёт по запросу. Минус: десятки минут в процессе API; запрос упадёт по
   тайм-ауту, а API будет занят.
4. Уведомитель раз в неделю запускает тот же скрипт отдельным процессом, итог кладёт в Redis, админка его
   показывает.

## Решение

Вариант 4 (`app/live_gate_job.py`).

- **Цели** — по статусам версий в БД. Версия в статусе forward — её собственный форвард. Версия в статусе backtest
  со своим списком инструментов, у которой есть «двойник» в форварде (те же правила, без списка), — кандидат:
  форвард двойника на списке кандидата (`--symbols-of`). Правило одной сделки действует по инструменту, поэтому
  такая выборка совпадает с тем, что дал бы сам кандидат (задача 11). Сейчас это 1.2.0 и кандидат 1.2.1.
- **Параметры отчёта** — бэктест с 01.06.2022 до дня начала форварда (`--to auto`), момент отчёта — последнее
  закрытие H4, итог сверки — из Redis.
- **Расписание** — понедельник после 02:00 UTC (после ежедневной сверки в 01:00), при старте — если отчёта нет;
  отчёт старше 8 дней строится в любой день. Если какая-то цель не построилась, весь набор строится заново через
  12 часов — например, когда версию перевели в форвард после последнего закрытия H4.
- **Процесс** — тот же скрипт (`sys.executable scripts/live_gate_report.py`), отдельный процесс с `nice 10` и
  тайм-аутом 60 минут на цель. Цикл уведомителя его не ждёт. Остановка уведомителя (выкладка) убивает процесс:
  он не держит остановку. Сбой одной цели записывается в её отчёт и не мешает остальным.
- **Хранение** — Redis `live_gate:last`: время, по каждой цели Markdown целиком и JSON-сводка (`summary_json`).
- **Показ** — `GET /v1/admin/live-gate` (только админ и владелец) и панель «Готовность к live» на вкладке
  «Стратегии»: число выполненных, невыполненных и требующих решения пунктов, таблица критериев, отчёт файлом.

Отчёт по-прежнему ничего не решает и статусов не меняет: выпуск в live — заявка владельца в той же вкладке.

## Последствия

- Владелец видит отчёт в админке. К 25.01.2027 (91 день форварда 1.2) там будет отчёт с пунктом о длине
  форварда.
- Раз в неделю сервер тратит десятки минут процессора с пониженным приоритетом и читает историю свечей. Если это
  станет заметно, бэктест-часть можно кешировать: её период фиксирован (до начала форварда).
- Отчёт содержит таблицу форвард-сигналов. Она видна только в админке, как и форвард-строки на сайте.
- Скрипт по-прежнему можно запустить руками (документ `docs/backtests/2026-11-12-live-gate-1.2.1-local.md`).
