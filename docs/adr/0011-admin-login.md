# ADR-0011. Отдельный вход в админку: свой сеанс и обязательная 2FA

Статус: предложено (ждёт подтверждения владельца). Дата: 2026-11-05; дополнено 2026-11-10 по итогам двух
проверок (безопасность и путь владельца) — см. «Что изменила проверка» — и переходным режимом до первой
настройки кода (решение Fable по поручению владельца от 2026-11-05) — см. «Переходный режим».
Задача: просьба владельца «нужно сделать вход для админа отдельно»; план 3.15 (админка), 6.8 (безопасность,
разделение ролей, аудит), 3.12 (2FA).

## Контекст

До этого решения админка `/admin` открывалась обычным входом на сайт: роль `owner`/`admin` лежит в
`users.role` (владелец получает её автоматически по `OWNER_EMAILS`, `auth.promote_owner`), а все
`/v1/admin/*` проверяли тот же access-токен сайта (`auth.require_role`). Следствия:

- кто завладел сессией сайта владельца (украденный refresh-cookie, XSS на публичной странице, чужой
  компьютер, где владелец не вышел), получал всю админку: роли, подписки, отмену сигналов, промокоды;
- 2FA была необязательной; ссылка «Админка» стояла в меню сайта;
- картинка кандидата в разметке (`<img src="/v1/admin/labels/…/image.png">`) не могла пройти проверку —
  браузер не добавляет заголовок `Authorization` к картинкам.

## Варианты

1. **Отдельный сеанс админки в httpOnly-cookie с путём `/v1/admin` и обязательной 2FA** (выбрано).
2. Требовать 2FA для роли admin/owner на обычном входе сайта: сессия сайта по-прежнему давала бы админку
   (30 дней refresh, тот же токен на публичных страницах), отдельного выхода нет.
3. Отдельный поддомен `admin.platformsol.com`: изоляция origin лучше, но нужен второй сервис/домен в Railway,
   CORS и cookie между доменами — непропорционально сейчас. Можно вернуться к этому, если появятся
   несколько админов или внешний аудит потребует (см. «Пересмотреть позже»).
4. Bearer-токен админки в `sessionStorage`: виден любому скрипту страницы (XSS), картинки разметки
   по-прежнему без токена.

## Решение

### Вход — страница `/admin/login`

- Не индексируется (`meta robots noindex`, `X-Robots-Tag: noindex, nofollow` на всех `/admin*`), не в
  sitemap (его нет), ссылок на неё с сайта и из меню нет — только по адресу.
- **Шаг 1** — email и пароль. Для аккаунтов без пароля (Google, вход по ссылке) — «войти по ссылке на почту»:
  письмо через `app.mail` (Resend), ссылка `/admin/login?link=…` живёт 10 минут и срабатывает один раз
  (`email_tokens.purpose = admin_magic`; ссылка входа на сайт сюда не подходит). Если почта на сервере
  не настроена (нет `RESEND_API_KEY` и окружение не local), API отвечает 503, а страница честно пишет, что вход
  по ссылке недоступен.
- Неизвестный адрес, неверный пароль, аккаунт без пароля, аккаунт без роли admin/owner, заблокированный —
  одна и та же ошибка «Не получилось войти. Проверьте email и пароль.» и одинаковая работа: пароль
  проверяется всегда (для несуществующего аккаунта — по пустышке Argon2). Письмо со ссылкой уходит в фоне,
  ответ `/magic` одинаковый для любого адреса.
- **Роль владельца — только для подтверждённой почты.** `promote_owner` даёт роль `owner` адресу из
  `OWNER_EMAILS`, только если `email_verified_at` заполнено, и сам почту подтверждённой не делает (раньше
  делал). Подтверждают почту: ссылка подтверждения, вход по ссылке и сброс пароля (письмо пришло на этот
  адрес), вход через Google с подтверждённым адресом, ссылка входа в админку — из письма или с сервера.
  Иначе тот, кто первым зарегистрировал адрес владельца (или заново — после удаления аккаунта), получал
  роль без доступа к ящику. Аккаунт с ролью admin/owner из сеанса сайта удалить нельзя (`DELETE /v1/me` → 403).
- Первый фактор даёт **билет** (15 минут, один раз, `email_tokens.purpose = admin_2fa_pw | admin_2fa_link`).
- **Шаг 2 — код обязателен.** Если 2FA уже есть — код из приложения или резервный код (сгорает).
- **Первая настройка кода — только после ссылки** (билет `admin_2fa_link`): верный пароль аккаунта без 2FA
  отвечает шагом `mail` и сам отправляет ссылку на адрес аккаунта; страница пишет «Проверьте почту». Если
  почта на сервере не настроена — страница говорит об этом и просит одноразовую ссылку с сервера:
  `python scripts/admin_link.py owner@example.com` (30 минут, один раз, строка `admin_login.link_by_script`
  в аудите). Одного пароля для привязки приложения мало: украденный пароль не открывает настройку, а письмо
  уходит в ящик настоящего владельца. По ссылке — новый секрет TOTP (всегда новый), QR-код (`segno`, путь
  SVG; тёмное на белом в любой теме — токены `--qr-dark/--qr-light`), кнопка `otpauth://` «Добавить код на
  этом устройстве» (на iPhone открывает «Пароли» → «Коды проверки», работает и Google Authenticator), ключ
  для ручного ввода. Первый верный код включает 2FA и выдаёт 10 резервных кодов. Подпись в приложении:
  **PlatformSol** (`twofactor.ISSUER`).
- **Из сеанса сайта админ 2FA не включает** (`/v1/me/2fa/setup` и `/enable` → 403; в настройках сайта вместо
  кнопки — пояснение). Иначе украденный пароль (вход на сайт без кода) или украденная сессия сайта привязали
  бы к админке чужое приложение. **И не отключает** (`/v1/me/2fa/disable` → 403, в настройках вместо формы —
  пояснение): без 2FA аккаунт вернулся бы в переходный режим, и админку снова открывал бы обычный вход на
  сайт — украденной сессии сайта и одного резервного кода для этого мало быть не должно. Новый телефон и новые
  резервные коды — в админке, «Защита входа».
- **Резервные коды** показываются один раз (копировать / скачать файлом, галочка «сохранил(а)»). До галочки
  они лежат в `sessionStorage` вкладки и переживают перезагрузку (на iPhone — уход в «Пароли», жест «потянуть
  вниз»); из админки, пока коды не подтверждены, возвращает к ним; после галочки стираются.
- **Код из приложения одноразовый — и в админке, и на сайте** (RFC 6238, 5.2): номер последнего принятого
  30-секундного шага хранится в `two_factor_secrets.last_step`, следующий код должен быть новее. Код, которым
  владелец вошёл в админку, нельзя повторить ни на входе сайта, ни при отключении 2FA, ни через полночь UTC.
  Строки 2FA, билетов и ссылок берутся под `SELECT … FOR UPDATE` до commit: два одновременных запроса с одним
  резервным кодом, одной ссылкой или одним билетом не проходят оба.
- 5-й неверный код сжигает билет (410) — снова пароль или ссылка; счёт идёт на весь срок жизни билета.
- Вход, первая настройка, выпуск резервных кодов и перенос кода присылают письмо владельцу аккаунта (время,
  IP, устройство, без секретов).
- Незаконченный вход хранится в `sessionStorage` вкладки (билет и показанный QR): iPhone выгружает вкладку,
  пока владелец добавляет код в «Пароли»; без этого QR сменился бы и добавленный код не подошёл.
- **Открытый сеанс не спрашивает вход заново:** закладка на `/admin/login` и ссылка `/admin?tab=…` из письма
  о тикете или из Telegram ведут сразу в админку. Подсказка `pl_admin_hint` — `SameSite=Lax` (браузер
  отправляет её при переходе по ссылке с другого сайта; секрета в ней нет), а страница входа с подсказкой
  сначала спрашивает `/v1/admin/auth/me`.

### Переходный режим: до первой настройки кода

Первая настройка кода возможна только по ссылке из письма (см. выше), а доставку писем владельцу в production
проверить нельзя: успешная отправка в журнал не пишется, у Fable нет доступа к почте владельца, DMARC у домена
нет (письмо может уйти в «Спам» или не дойти). Запустить `scripts/admin_link.py` на сервере тоже некому: ни у
владельца, ни у Fable нет консоли на хостинге. Если бы строгий вход действовал сразу для всех, недошедшее
письмо оставило бы владельца без админки. Поэтому:

- **Строгий вход обязателен только для аккаунта, у которого 2FA включена.** Пока у админа или владельца её нет,
  `/v1/admin/*` (всё, что закрыто `require_admin`, и `GET /v1/admin/auth/me`) принимает, кроме сеанса админки,
  обычный токен сайта (`Authorization: Bearer`) — как до этого решения: роль admin/owner, аккаунт не
  заблокирован и не удалён, `twofactor.is_enabled(...) == False` (`admin_auth.admin_access`). API-ключ
  (`X-API-Key`) не подходит. Заголовок против CSRF для такого запроса не нужен (токен не cookie, чужой сайт его
  не подставит); проверка `site_proxy_only` остаётся.
- **Сначала — сеанс админки.** Есть cookie `pl_admin` — решает она; закрытый сеанс отвечает своей причиной
  (`X-Admin-Ended`), даже если рядом пришёл токен сайта.
- **Отказы понятные:** 2FA включена — 401 «Нужен вход в админку.»; не админ — 403; заблокирован — 403
  «Аккаунт заблокирован.»; удалён или токен поддельный — 401.
- **`/v1/admin/auth/me`** по токену сайта отвечает `method: "site"`, `grace: true`, `setup_required: true`,
  без сроков сеанса; по cookie — как раньше, с `grace: false`.
- **Аудит:** каждое действие админки в этом режиме — с отметкой `access: "grace"` в `payload`: видно, что оно
  сделано без 2FA.
- **Права админки без кода не выдаются:** повышение до admin/owner в этом режиме — 403 «сначала настройте
  защиту входа кодом». Действия с кодом (`/2fa/backup-codes`, `/2fa/rotate`, выход) — только в сеансе админки.
- **Сайт:** `/admin` без сеанса админки, но со входом на сайт (`pl_auth`) открывает оболочку админки; она
  спрашивает API и, если `grace: true`, показывает админку с постоянной плашкой «Вход в админку пока без
  защиты кодом. Настройте защиту — это одна минута» и кнопкой «Настроить». Клиент админки
  (`lib/admin-auth.ts`) в этом режиме шлёт токен сайта, как раньше. `grace: false` и сеанса нет — на
  `/admin/login`, как раньше. Ссылки «Админка» в меню сайта по-прежнему нет.
- **Настройка из переходного режима** — `/admin/login?setup=1`: тот же вход (пароль → письмо → QR → код →
  резервные коды) с объяснением, email подставлен. На шаге «Проверьте почту» такому владельцу показано, что
  админка пока открыта по адресу `/admin`, и кнопка «Отправить письмо ещё раз» (`/v1/admin/auth/magic`, те же
  лимиты: 3 письма в час на адрес). **Способа настроить код без письма нет** — иначе вернулась бы SEC-1.
- **Конец режима.** Первый верный код включает 2FA, и с этого момента токен сайта в админку этого аккаунта не
  пускает — без отдельного переключателя. Вернуться в режим нельзя: отключить 2FA на сайте админу запрещено.
  Единственный путь назад — сброс на сервере (`scripts/admin_2fa_reset.py`, см. «Восстановление»).

### Сеанс админки

- Токен — JWT `HS256` c `scope=admin`, `aud=platformsol-admin`, `sid`, `iat`, `exp`; ключ —
  `HMAC-SHA256(JWT_SECRET, "platformsol:admin-session:v1")`. Токен сайта не проходит проверку админки
  (другой ключ, нет `aud`/`scope`), токен админки не проходит проверку сайта (другой ключ, лишний `aud`).
- Хранится в httpOnly-cookie `pl_admin`: `Path=/v1/admin`, `SameSite=Strict`, `Secure` (кроме local).
  Браузер отправляет её только на `/v1/admin/*` (через прокси Next — first-party), скрипты страницы её не
  видят. `Max-Age` — 8 ч + сутки: сам сеанс живёт 8 часов (срок в токене и в таблице), а cookie остаётся,
  чтобы API мог ответить «прошло 8 часов», а не «нет входа». Для редиректов в `src/proxy.ts` — подсказка без
  секрета `pl_admin_hint=1` (`Path=/admin`, `SameSite=Lax`), как `pl_auth` у сайта.
- Таблица `admin_sessions` (миграция `0022_admin`): `id` (= `sid`), пользователь, способ первого фактора,
  создан, последнее действие, истекает, отозван и почему (`revoked_reason`), IP, браузер. На каждый запрос: строка есть и не отозвана, не старше
  **8 часов** с входа, без простоя дольше **1 часа** (отметка обновляется не чаще раза в минуту). Refresh-токена
  нет: через 8 часов — новый вход с кодом.
- Почему таблица, а не номер версии сеанса в `users`: простой в 1 час требует состояния на сервере, выход
  из админки должен отзывать токен сразу, а владелец видит в аудите, какой сеанс что делал (`session` — первые
  8 символов `sid`). Отзыв всех сеансов пользователя — `admin_auth.revoke_user_sessions`.
- **Отзыв:** смена пароля (`/v1/me/password`), новый пароль по ссылке сброса (`/v1/auth/reset/confirm`),
  перенос кода на другой телефон (кроме текущего сеанса), сброс 2FA на сервере, смена роли и блокировка из
  админки — закрывают сеансы админки этого пользователя. Отключение 2FA на сайте (`/v1/me/2fa/disable`) тоже
  закрывает сеансы, но админу оно запрещено (403); сработает для того, у кого роль уже сняли. Понижение роли, блокировка или удаление
  аккаунта к тому же проверяются на каждый запрос.
- **Причина закрытия доходит до владельца:** ответ 401/403 несёт заголовок `X-Admin-Ended` (`idle`, `expired`,
  `logout`, `password`, `2fa`, `role`, `blocked`, `gone`), прокси Next его пропускает, страница входа пишет
  своё для каждой причины («пароль аккаунта изменён», «больше часа без действий», «прошло 8 часов»…).
  Подделанный токен причины не получает (`gone`).
- **Выход раздельный:** `POST /v1/admin/auth/logout` отзывает сеанс админки и удаляет `pl_admin`, сессию сайта
  (`refresh_token` на `/v1/auth`, `pl_auth`) не трогает; выход с сайта не трогает админку.
- **CSRF:** кроме `SameSite=Strict`, изменяющие запросы к `/v1/admin/*` требуют заголовок
  `X-Requested-With: platformsol-admin` (чужой сайт не может его поставить без CORS-разрешения; прокси Next
  его передаёт). GET-запросы (в том числе картинка разметки) идут без заголовка.

### Защита входа внутри админки (вкладка «Защита входа»)

- **Новые резервные коды** — `POST /v1/admin/auth/2fa/backup-codes` по коду из приложения (резервным кодом
  новые не выпускаются — нужен телефон); старые перестают работать.
- **Перенос кода на другой телефон** — `/2fa/rotate` (текущий код или резервный → новый QR) и
  `/2fa/rotate/confirm` (код с нового телефона): секрет заменяется, выдаются новые резервные коды, другие
  сеансы админки закрываются. Защита при этом не выключается ни на секунду; ожидающий секрет живёт 15 минут
  в подписанном токене, привязанном к этому сеансу.
- **Повысить роль до admin или owner** можно только с кодом из приложения (`code` в
  `PATCH /v1/admin/users/{id}`): см. модель угроз, «скрипт на странице сайта». Понижение и роль support — без кода.
- Лимит кодов на аккаунт (10 неверных за 15 минут) общий для входа и этих действий.

### Что закрыто сеансом админки

`admin_auth.require_admin` — единственная проверка для всех `/v1/admin/*`: стратегии и заявки на статус,
инструменты, сигналы (отмена), пользователи (роли, блокировка, выдача подписки — биллинг), промокоды,
тикеты поддержки (ответы и статусы), системный статус, аудит, разметка фигур `/v1/admin/labels/*`.
Пускает сеанс админки, а токен сайта — только в переходном режиме (2FA у аккаунта не включена).
`auth.require_role` удалён, чтобы проверку по одному токену сайта нельзя было вернуть по ошибке.

Не входят в админку и не меняются:

- `/debug/*` (визуальная проверка движка, `/debug/live`) — служебные адреса API со своим `DEBUG_TOKEN`
  в `?token=`; выключены, пока токен не задан. Токен сайта их никогда не открывал. Рекомендация: в production
  `DEBUG_TOKEN` не задавать или менять после каждой проверки.
- Роль admin/owner на сайте по-прежнему даёт уровень доступа Premium к **чтению** данных (форвард-сигналы,
  лимиты LLM, кнопки для «своих» в терминале) — это не права админки и ничего не меняет в данных.

### Лимиты попыток (`ratelimit.py`, режим `strict`)

Пароль: 5 неудач за 15 минут на адрес (с `PROXY_SECRET` — на адрес + IP) и 10 с одного IP; код: 10 неверных за 15 минут на аккаунт и 20
запросов с IP; 5-й неверный код сжигает билет; письмо со ссылкой: 3 в час на адрес и 10 с IP.

- **Считаются неудачи.** Попытка занимается до проверки (одновременные запросы не превышают лимит), верный
  пароль и верный код её возвращают: владелец не запирает себя обычными входами.
- **Чужой перебор не запирает владельца.** Две защиты:
  1. Браузер, где админ уже прошёл второй фактор, получает cookie устройства `pl_admin_device` (httpOnly,
     `Path=/v1/admin/auth`, 180 дней, подписана своим ключом, входа не даёт). С ней лимит пароля и писем
     считается по устройству, а не по адресу почты: тот, кто знает адрес владельца и шлёт неверные пароли,
     упирается в свой лимит, а владелец входит. Неверные пароли с самого устройства считаются так же.
  2. С `PROXY_SECRET` (IP клиента называет прокси сайта, подставить его нельзя) лимит пароля и писем для
     остальных браузеров идёт на пару «адрес почты + IP»: перебор с одного IP запирает только себя, а
     владелец со своего IP входит и с нового устройства. Распределённый перебор ограничивает общий потолок
     по адресу — 50 неудач за 15 минут и 10 писем в час со всех IP.
  Без `PROXY_SECRET` IP верить нельзя, и для незнакомого браузера лимит остаётся по адресу почты.
- **Окна скользящие** (текущее окно + доля прошлого): на стыке окон нет двойного запаса попыток. Счётчик
  неверных кодов билета живёт весь срок билета, без привязки к часам.
- При сбое Redis счёт идёт в памяти процесса (у сайта сбой Redis по-прежнему пропускает попытку).
- Отказы по лимиту и несуществующие билеты в аудит не пишутся; строк без пользователя (неизвестный адрес) —
  не больше 30 в минуту: перебор не вытесняет из журнала настоящие события.

### Адрес клиента и прокси сайта (`PROXY_SECRET`)

- В лимиты, аудит, `admin_sessions.ip` и письма попадает только правильный IP-адрес (`ipaddress`): текст из
  заголовка («это были вы») туда не проходит.
- Если на сервисах `api` и `web` задан один и тот же `PROXY_SECRET`, прокси Next (`/v1`) добавляет к запросу
  секрет и адрес клиента, который увидел сам (`X-Real-IP` от входного узла хостинга, иначе последнее значение
  `X-Forwarded-For`), а API верит только такому адресу и открывает `/v1/admin/*` **только через сайт**
  (напрямую по адресу API — 403). Заголовки `x-pl-*` от браузера прокси не пропускает.
- Без `PROXY_SECRET` всё работает как раньше: IP — первое значение `X-Forwarded-For`, его может подставить
  клиент (см. «Известные ограничения»).

### Аудит

Каждая попытка — строка `admin_audit` с `target=admin_login`: `admin_login.failed` (причина: unknown_email,
bad_password, no_password, not_admin, blocked, deleted), `password_ok`, `link_sent` / `link_refused` /
`link_used` / `link_failed` / `link_by_script`, `setup_started`, `setup_code_failed`, `setup_done`,
`code_failed` (и сгорел ли билет), `success` (способ, фактор, сколько резервных кодов осталось), `admin_logout`;
действия с защитой: `admin_2fa.backup_codes_reissued`, `rotate_started`, `rotated`, `code_failed`,
`reset_by_script`; выдача роли — `user.role` (`confirmed: code`) и `user.role_code_failed`. Действия админки в
переходном режиме (по токену сайта, без 2FA) — с отметкой `access: "grace"`.
В каждой строке входа — IP и браузер. Паролей, кодов, ключей, билетов и ссылок нет. Попытка с неизвестным
адресом пишется без пользователя (`actor_id` пустой — миграция `0022_admin`) с адресом под маской
`o***@example.com`.

## Известные ограничения

- **Отдельного origin нет** — см. строку про XSS выше. Это главное, что остаётся незакрытым.
- **Адрес клиента зависит от хостинга.** С `PROXY_SECRET` прокси сайта берёт `X-Real-IP`. По документации
  Railway его ставит входной узел; перезаписывает ли он значение, присланное клиентом, не проверено (в
  production мы ничего не меняли). Проверка при выкладке: войти в админку и сравнить IP в строке аудита со
  своим; затем один запрос входа с подставленным `X-Real-IP` — IP в аудите измениться не должен. Если
  меняется — лимиты по IP ненадёжны (по адресу, устройству и аккаунту — остаются), а IP в аудите и письме
  считать подсказкой. Без `PROXY_SECRET` — как раньше: первое значение `X-Forwarded-For`.
- **Резервные коды и незаконченный вход лежат в `sessionStorage`** до подтверждения: скрипт на этой странице
  их прочитал бы. Срок — минуты, только в этой вкладке; иначе перезагрузка теряла коды навсегда.
- **Аккаунт, заведённый на адрес владельца раньше него** (чужой пароль, почта не подтверждена): роли и
  настройки кода не получает. Когда настоящий владелец подтвердит почту (сброс пароля — он же меняет пароль,
  или вход через Google), роль получит этот аккаунт. После входа через Google пароль такого аккаунта надо
  сменить через «Забыли пароль?» — старый мог знать тот, кто завёл аккаунт. В админку ему всё равно нужен код.
- **Переходный режим держится, пока владелец не настроит код.** Срока у него нет: выключать админку по таймеру
  при недошедшем письме — тот самый риск потерять доступ, ради которого режим введён. Напоминание — плашка.
- Отключить 2FA на сайте админ не может; телефон меняют через «Защита входа» → «Новый телефон», не отключая
  защиту. После сброса на сервере новая настройка — снова через письмо (или `scripts/admin_link.py`), а до неё
  аккаунт в переходном режиме.
- **Доставка писем не проверена.** На домене есть DKIM (`resend._domainkey`) и SPF для `send.platformsol.com`,
  ключ Resend задан у сервиса API; DMARC нет — письмо может попасть в «Спам». Успешная отправка в журнал не
  пишется, поэтому дошло ли письмо, видно только в ящике владельца.

## Восстановление

1. **Потерян телефон, резервные коды есть** — на шаге кода ввести резервный код (каждый один раз), затем в
   админке: «Защита входа» → «Новый телефон» → резервный код → QR-код на новом телефоне → код с него. Защита
   не выключается, выдаются новые резервные коды. Если коды в «Паролях» iCloud — они уже на новом iPhone.
2. **Резервные коды потеряны или кончаются, телефон есть** — «Защита входа» → «Выпустить новые коды» (по
   коду из приложения). В шапке админки — предупреждение, когда осталось 3 кода и меньше.
3. **Потеряны и телефон, и резервные коды** — только с доступом к серверу (это и есть подтверждение
   личности): one-off команда `python scripts/admin_2fa_reset.py owner@example.com` — удаляет секрет и коды,
   закрывает сеансы админки, пишет `admin_2fa.reset_by_script` в аудит. До новой настройки аккаунт в переходном
   режиме: админку открывает вход на сайт, сверху плашка. Новая настройка: «Настроить» → пароль → письмо со
   ссылкой → QR-код. Без почты на сервере — `python scripts/admin_link.py owner@example.com`
   печатает такую же ссылку (30 минут, один раз). Оба скрипта — только для admin/owner и адресов из
   `OWNER_EMAILS`.
4. **Забыт пароль и не настроена почта** — `scripts/reset_link.py` (уже был): одноразовая ссылка смены
   пароля владельца из `OWNER_EMAILS`.
5. **Вход заперт лимитом** (кто-то перебирает пароль по адресу владельца, а вход нужен с нового устройства) —
   подождать 15 минут или взять ссылку с сервера (`scripts/admin_link.py`): по ней — сразу шаг кода.

Сбрасывать 2FA другим админам из админки сознательно нельзя: скомпрометированный админ иначе снимал бы
защиту с чужих аккаунтов.

## Последствия

- **Сразу после выкладки ничего не ломается:** у владельца 2FA нет, поэтому `/admin` открывается, как сегодня, —
  по входу на сайт, но с плашкой «Вход в админку пока без защиты кодом. Настройте защиту — это одна минута».
  Доступ к админке не зависит от того, дойдёт ли письмо.
- **Настройка** — «Настроить» → пароль → письмо со ссылкой → QR-код в «Пароли» → первый код → резервные коды
  (минута). Письмо не пришло — проверить «Спам», нажать «Отправить письмо ещё раз»; админка всё это время
  открыта. Ссылка с сервера (`python scripts/admin_link.py <адрес владельца>`) остаётся запасным путём для того,
  у кого есть консоль хостинга (сейчас её нет ни у владельца, ни у Fable).
- **После настройки** владелец входит в админку отдельно: `/admin/login` → пароль → код из «Пароли». Каждые
  8 часов (или после часа без действий) — вход заново; открытый сеанс по закладке и по ссылке из письма вход не
  спрашивает. Вход на сайт админку больше не открывает; вернуть переходный режим можно только сбросом на сервере.
- Владелец, у которого роль `owner` уже есть, её сохраняет. Новый адрес в `OWNER_EMAILS` получает роль после
  подтверждения почты (письмо или ссылка с сервера).
- 2FA, включённая на входе в админку, — общая с сайтом (одна строка `two_factor_secrets`): вход на сайт тоже
  станет спрашивать код. Это сильнее, а не слабее. Код, принятый в одном месте, во втором не повторить —
  нужен следующий (30 секунд).
- Ссылки «Админка» больше нет в меню сайта; закладку на `/admin` или `/admin/login` можно оставить.
- Новая зависимость API: `segno` (QR-код, чистый Python, без системных библиотек).
- Новая настройка `PROXY_SECRET` (одинаковая у сервисов `api` и `web`; без неё поведение прежнее).
- Миграция `0022_admin` (после `0021`) добавляет таблицу `admin_sessions`, столбец
  `two_factor_secrets.last_step` и снимает NOT NULL с `admin_audit.actor_id`; данные не меняет. Откат удаляет
  строки аудита без пользователя, таблицу сеансов и столбец. Идентификатор `0022` оставлен соседней ветке
  (область сигнала при публикации), которая тоже продолжает `0021`: при сведении веток вторую ревизию
  цепляют за первую (меняется только `down_revision`); тест `tests/test_migrations.py` не даст выложить две
  головы или два одинаковых идентификатора.

| GRACE: письмо для первой настройки может не дойти, а консоли на сервере нет — владелец потерял бы админку | Переходный режим: до включения 2FA админку открывает вход на сайт (с плашкой и отметкой `access: "grace"` в аудите); настройка — по-прежнему только по письму, «Отправить письмо ещё раз»; после настройки — только строгий вход. Отключать 2FA на сайте админу запрещено. |

## Пересмотреть позже

- **Отдельный поддомен для админки** (`admin.platformsol.com`, cookie только на нём) — единственное, что
  закрывает XSS на сайте при открытом сеансе админки. Нужны домен и настройка сервиса `web` в Railway;
  рекомендуется сделать до появления второго админа или платежей через админку.
- Код из телефона на остальные необратимые действия (выдача подписки, решение по статусу стратегии) — если
  отдельный origin откладывается надолго.
- WebAuthn (passkey/Face ID) вместо TOTP.
- Проверить поведение `X-Real-IP` на Railway и записать результат сюда.
- Добавить DMARC для `platformsol.com` и запись об успешной отправке письма в журнал — тогда о недошедшем письме
  будет видно не только в ящике владельца.
- Когда владелец настроит код: убедиться по аудиту, что действий с `access: "grace"` больше нет.
