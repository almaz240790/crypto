# ADR-0011. Отдельный вход в админку: свой сеанс и обязательная 2FA

Статус: предложено (ждёт подтверждения владельца). Дата: 2026-11-05.
Задача: просьба владельца «нужно сделать вход для админа отдельно»; план 3.15 (админка), 6.8 (безопасность,
разделение ролей, аудит), 3.12 (2FA).

## Контекст

До этого решения админка `/admin` открывалась обычным входом на сайт: роль `owner`/`admin` лежит в
`users.role` (владелец получает её автоматически по `OWNER_EMAILS`, `auth.promote_owner`), а все
`/v1/admin/*` проверяли тот же access-токен сайта (`auth.require_role`). Следствия:

- кто завладел сессией сайта владельца (украденный refresh-cookie, XSS на публичной странице, чужой
  компьютер, где владелец не вышел), получал всю админку: роли, подписки, отмену сигналов, промокоды;
- 2FA была необязательной; ссылка «Админка» стояла в меню сайта;
- картинка кандидата в разметке (`<img src="/v1/admin/labels/…/image.png">`) не могла пройти проверку —
  браузер не добавляет заголовок `Authorization` к картинкам.

## Варианты

1. **Отдельный сеанс админки в httpOnly-cookie с путём `/v1/admin` и обязательной 2FA** (выбрано).
2. Требовать 2FA для роли admin/owner на обычном входе сайта: сессия сайта по-прежнему давала бы админку
   (30 дней refresh, тот же токен на публичных страницах), отдельного выхода нет.
3. Отдельный поддомен `admin.platformsol.com`: изоляция origin лучше, но нужен второй сервис/домен в Railway,
   CORS и cookie между доменами — непропорционально сейчас. Можно вернуться к этому, если появятся
   несколько админов или внешний аудит потребует (см. «Пересмотреть позже»).
4. Bearer-токен админки в `sessionStorage`: виден любому скрипту страницы (XSS), картинки разметки
   по-прежнему без токена.

## Решение

### Вход — страница `/admin/login`

- Не индексируется (`meta robots noindex`, `X-Robots-Tag: noindex, nofollow` на всех `/admin*`), не в
  sitemap (его нет), ссылок на неё с сайта и из меню нет — только по адресу.
- **Шаг 1** — email и пароль. Для аккаунтов без пароля (Google, вход по ссылке) — «войти по ссылке на почту»:
  письмо через `app.mail` (Resend), ссылка `/admin/login?link=…` живёт 10 минут и срабатывает один раз
  (`email_tokens.purpose = admin_magic`; ссылка входа на сайт сюда не подходит). Если почта на сервере
  не настроена (нет `RESEND_API_KEY` и окружение не local), API отвечает 503, а страница честно пишет, что вход
  по ссылке недоступен.
- Неизвестный адрес, неверный пароль, аккаунт без пароля, аккаунт без роли admin/owner, заблокированный —
  одна и та же ошибка «Не получилось войти. Проверьте email и пароль.» и одинаковая работа: пароль
  проверяется всегда (для несуществующего аккаунта — по пустышке Argon2). Письмо со ссылкой уходит в фоне,
  ответ `/magic` одинаковый для любого адреса.
- `promote_owner` вызывается после верного пароля и при запросе ссылки: адрес из `OWNER_EMAILS` становится
  владельцем, как и раньше.
- Первый фактор даёт **билет** (15 минут, один раз, `email_tokens.purpose = admin_2fa_pw | admin_2fa_link`).
- **Шаг 2 — код обязателен.** Если 2FA у аккаунта ещё нет — первая настройка: новый секрет TOTP (всегда новый:
  незавершённый секрет, созданный из сеанса сайта, не используется), QR-код (`segno`, путь SVG; тёмное на
  белом в любой теме — токены `--qr-dark/--qr-light`), кнопка `otpauth://` «Добавить код на этом устройстве»
  (на iPhone открывает «Пароли» → «Коды проверки», работает и Google Authenticator), ключ для ручного ввода.
  Первый верный код включает 2FA и выдаёт 10 резервных кодов — показываются один раз (копировать / скачать
  файлом, галочка «сохранил»). Если 2FA уже есть — код из приложения или резервный код (сгорает).
  Подпись в приложении: **PlatformSol** (`twofactor.ISSUER`).
- Один и тот же код TOTP (30-секундный шаг) второй раз не принимается — подсмотренный код бесполезен.
- 5-й неверный код сжигает билет (410) — снова пароль или ссылка.
- Вход и первая настройка присылают письмо владельцу аккаунта (время, IP, устройство, без секретов).
- Незаконченный вход хранится в `sessionStorage` вкладки (билет и показанный QR): iPhone выгружает вкладку,
  пока владелец добавляет код в «Пароли»; без этого QR сменился бы и добавленный код не подошёл.

### Сеанс админки

- Токен — JWT `HS256` c `scope=admin`, `aud=platformsol-admin`, `sid`, `iat`, `exp`; ключ —
  `HMAC-SHA256(JWT_SECRET, "platformsol:admin-session:v1")`. Токен сайта не проходит проверку админки
  (другой ключ, нет `aud`/`scope`), токен админки не проходит проверку сайта (другой ключ, лишний `aud`).
- Хранится в httpOnly-cookie `pl_admin`: `Path=/v1/admin`, `SameSite=Strict`, `Secure` (кроме local),
  `Max-Age` 8 ч. Браузер отправляет её только на `/v1/admin/*` (через прокси Next — first-party), скрипты
  страницы её не видят. Для редиректов в `src/proxy.ts` — подсказка без секрета `pl_admin_hint=1`
  (`Path=/admin`), как `pl_auth` у сайта.
- Таблица `admin_sessions` (миграция 0022): `id` (= `sid`), пользователь, способ первого фактора, создан,
  последнее действие, истекает, отозван, IP, браузер. На каждый запрос: строка есть и не отозвана, не старше
  **8 часов** с входа, без простоя дольше **1 часа** (отметка обновляется не чаще раза в минуту). Refresh-токена
  нет: через 8 часов — новый вход с кодом.
- Почему таблица, а не номер версии сеанса в `users`: простой в 1 час требует состояния на сервере, выход
  из админки должен отзывать токен сразу, а владелец видит в аудите, какой сеанс что делал (`session` — первые
  8 символов `sid`). Отзыв всех сеансов пользователя — `admin_auth.revoke_user_sessions`.
- **Отзыв:** смена пароля (`/v1/me/password`), новый пароль по ссылке сброса (`/v1/auth/reset/confirm`),
  отключение 2FA (`/v1/me/2fa/disable`), смена роли и блокировка из админки — закрывают все сеансы админки
  этого пользователя. Понижение роли, блокировка или удаление аккаунта к тому же проверяются на каждый запрос.
- **Выход раздельный:** `POST /v1/admin/auth/logout` отзывает сеанс админки и удаляет `pl_admin`, сессию сайта
  (`refresh_token` на `/v1/auth`, `pl_auth`) не трогает; выход с сайта не трогает админку.
- **CSRF:** кроме `SameSite=Strict`, изменяющие запросы к `/v1/admin/*` требуют заголовок
  `X-Requested-With: platformsol-admin` (чужой сайт не может его поставить без CORS-разрешения; прокси Next
  его передаёт). GET-запросы (в том числе картинка разметки) идут без заголовка.

### Что закрыто сеансом админки

`admin_auth.require_admin` — единственная проверка для всех `/v1/admin/*`: стратегии и заявки на статус,
инструменты, сигналы (отмена), пользователи (роли, блокировка, выдача подписки — биллинг), промокоды,
тикеты поддержки (ответы и статусы), системный статус, аудит, разметка фигур `/v1/admin/labels/*`.
`auth.require_role` удалён, чтобы проверку по токену сайта нельзя было вернуть по ошибке.

Не входят в админку и не меняются:

- `/debug/*` (визуальная проверка движка, `/debug/live`) — служебные адреса API со своим `DEBUG_TOKEN`
  в `?token=`; выключены, пока токен не задан. Токен сайта их никогда не открывал. Рекомендация: в production
  `DEBUG_TOKEN` не задавать или менять после каждой проверки.
- Роль admin/owner на сайте по-прежнему даёт уровень доступа Premium к **чтению** данных (форвард-сигналы,
  лимиты LLM, кнопки для «своих» в терминале) — это не права админки и ничего не меняет в данных.

### Лимиты попыток (`ratelimit.py`, режим `strict`)

Пароль: 5 попыток за 15 минут на адрес и 10 с одного IP; код: 10 за 15 минут на аккаунт и 20 с IP; письмо
со ссылкой: 3 в час на адрес и 10 с IP. Для входа в админку при сбое Redis счёт идёт в памяти процесса
(у сайта сбой Redis по-прежнему пропускает попытку). Отказы по лимиту в аудит не пишутся (иначе перебор
раздувал бы таблицу); попытки до лимита — пишутся.

### Аудит

Каждая попытка — строка `admin_audit` с `target=admin_login`: `admin_login.failed` (причина: unknown_email,
bad_password, no_password, not_admin, blocked, deleted), `password_ok`, `link_sent` / `link_refused` /
`link_used` / `link_failed`, `ticket_invalid`, `setup_started`, `setup_code_failed`, `setup_done`,
`code_failed` (и сгорел ли билет), `success` (способ, фактор, сколько резервных кодов осталось), `admin_logout`.
В каждой — IP и браузер. Паролей, кодов, ключей, билетов и ссылок нет. Попытка с неизвестным адресом пишется
без пользователя (`actor_id` пустой — миграция 0022) с адресом под маской `o***@example.com`.

## Модель угроз

| Угроза | Что мешает |
|---|---|
| Украдена сессия сайта владельца (cookie, XSS на публичной странице, чужой компьютер) | Сессия сайта не открывает `/v1/admin/*`; нужен пароль или почта и код из телефона. Админ без пароля не может задать пароль из сеанса сайта (`/v1/me/password` → 403: только «Забыли пароль?» по письму). Отключить 2FA из сеанса сайта нельзя без кода. |
| Украден пароль | Без кода из телефона (или резервного кода) вход не завершается; письмо о каждом входе. |
| Перебор паролей и кодов | Лимиты по адресу, IP, аккаунту и билету; одинаковая ошибка и время. TOTP: 10 попыток за 15 минут при 3 верных кодах из миллиона — порядка года перебора, и каждый билет требует пароль. |
| Перебор адресов админов | Одинаковые ответы и время у `/login` и `/magic`; письмо уходит в фоне. |
| Подсмотренный код | Код (шаг TOTP) одноразовый. |
| Кража токена админки | httpOnly, путь `/v1/admin`, SameSite=Strict; 1 час простоя, 8 часов максимум; выход и смена пароля отзывают на сервере. |
| CSRF | SameSite=Strict + обязательный заголовок для изменяющих запросов. |
| Злоумышленник с сеансом сайта заранее включил 2FA своим приложением, пока владелец её не настроил | Получает только отказ в обслуживании (владелец не войдёт), не админку: нужен ещё пароль/почта. Восстановление — скрипт ниже. |
| Первая настройка 2FA тем, у кого есть пароль владельца, раньше самого владельца | Принцип «доверие при первом использовании»: защищает пароль/почта. Смягчение: письмо «включена защита админки» и строка аудита; владельцу — настроить код сразу после выкладки. |

Известные ограничения: IP для лимитов берётся из первого значения `X-Forwarded-For` (как у входа сайта);
если хостинг пропускает заголовок клиента, лимит по IP обходится сменой заголовка — лимиты по адресу и
аккаунту остаются. Проверить на Railway и при необходимости брать последний доверенный адрес.

## Восстановление

1. **Потерян телефон, коды есть** — на шаге кода ввести резервный код (каждый один раз). Затем на сайте:
   «Настройки» → двухфакторная защита → отключить (резервным кодом); следующий вход в админку снова
   предложит настройку с новым QR и новыми кодами. Если коды в «Паролях» iCloud — они уже на новом iPhone.
2. **Потеряны и телефон, и резервные коды** — только с доступом к серверу (это и есть подтверждение личности):
   one-off команда в Railway `python scripts/admin_2fa_reset.py owner@example.com` — удаляет секрет и коды,
   закрывает сеансы админки, пишет `admin_2fa.reset_by_script` в аудит; следующий вход — первая настройка.
   Скрипт работает только для admin/owner и адресов из `OWNER_EMAILS`.
3. **Забыт пароль и не настроена почта** — `scripts/reset_link.py` (уже был): одноразовая ссылка смены пароля
   владельца из `OWNER_EMAILS`.

Сбрасывать 2FA другим админам из админки сознательно нельзя: скомпрометированный админ иначе снимал бы
защиту с чужих аккаунтов.

## Последствия

- Владелец входит в админку отдельно: `/admin/login` → пароль → код из «Пароли». В первый раз — настройка
  кода (минута) и резервные коды. Каждые 8 часов (или после часа без действий) — вход заново.
- 2FA, включённая на входе в админку, — общая с сайтом (одна строка `two_factor_secrets`): вход на сайт тоже
  станет спрашивать код. Это сильнее, а не слабее.
- Ссылки «Админка» больше нет в меню сайта; закладку на `/admin` можно оставить — без сеанса она ведёт на
  `/admin/login`.
- Новая зависимость API: `segno` (QR-код, чистый Python, без системных библиотек).
- Миграция 0022 только добавляет таблицу и снимает NOT NULL с `admin_audit.actor_id`; данные не меняет.
  Откат удаляет строки аудита без пользователя и таблицу сеансов.

## Пересмотреть позже

- Отдельный поддомен для админки и WebAuthn (passkey/Face ID) вместо TOTP — когда админов станет больше одного.
- Перевыпуск резервных кодов из админки по текущему коду (сейчас — через отключение и повторную настройку).
- Доверенный IP из заголовков хостинга для лимитов.
